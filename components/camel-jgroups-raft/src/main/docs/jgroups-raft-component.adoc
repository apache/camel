:doctitle: JGroups raft
:shortname: jgroups-raft
:artifactid: camel-jgroups-raft
:description: Append data to the replicated log of a JGroups-raft cluster, and receive the leader and follower role changes of the local member.

*Since Camel {since}*

*{component-header}*

http://belaban.github.io/jgroups-raft/[JGroups-raft] is a https://raftconsensus.github.io/[Raft] implementation in http://www.jgroups.org/[JGroups].
The *jgroups-raft:* component provides interoperability between camel and a JGroups-raft clusters.

Maven users will need to add the following dependency to their `pom.xml`
for this component.

[source,xml]
----
<dependency>
    <groupId>org.apache.camel</groupId>
    <artifactId>camel-jgroups-raft</artifactId>
    <!-- use the same version as your Camel core version -->
    <version>x.y.z</version>
</dependency>
----

== URI format

----
jgroups-raft:clusterName[?options]
----

Where *clusterName* represents the name of the JGroups-raft cluster, the
component should connect to.

== Channel configuration

The `channelProperties` option (of the endpoint or the component) sets the JGroups XML configuration of the channel,
as a file, a URL or a classpath resource. When it is not set, the endpoint uses `raft.xml`, which is the configuration
in the `camel-jgroups-raft` JAR unless the application has its own `raft.xml` first on the classpath. The
`jgroupsConfig` option of the `JGroupsRaftClusterService` has the same default.

The `raft.xml` in the JAR is a sample for development and tests:

* it uses UDP multicast (`228.5.5.5`), without authentication or encryption, so any host on the same network that uses
the same cluster name can join the cluster and take part in the Raft log, and the messages are sent in clear text;
* it lists `A` as the only member in the `members` attribute of `RAFT`.

A WARN is logged when an endpoint (or the cluster service) starts with this default. In production, use your own
JGroups configuration, under another name, with:

* the `AUTH` protocol, and `SYM_ENCRYPT` or `ASYM_ENCRYPT`, so that only trusted members join the cluster and the
messages are encrypted;
* the Raft IDs of all the members of the cluster in the `members` attribute of `RAFT` (for example
`members="node1,node2,node3"`), and the `raft_id` of each member;
* a transport that fits the network, such as TCP with a list of the members, when multicast is not wanted.

[source,java]
----
from("direct:start").to("jgroups-raft:clusterName?raftId=node1&channelProperties=my-raft.xml");
----

See the http://belaban.github.io/jgroups-raft/[JGroups-raft] and http://www.jgroups.org/[JGroups] documentation for
the protocols.

== Usage

Using `jgroups-raft` component with `enableRoleChangeEvents=true` on the consumer side of the route will capture
change in JGroups-raft role and forward them to the Camel route.
JGroups-raft consumer processes incoming messages
http://camel.apache.org/asynchronous-routing-engine.html[asynchronously].

[tabs]
====
Java::
+
[source,java]
----
from("jgroups-raft:clusterName?enableRoleChangeEvents=true").to("seda:queue");
----

XML::
+
[source,xml]
----
<route>
  <from uri="jgroups-raft:clusterName?enableRoleChangeEvents=true"/>
  <to uri="seda:queue"/>
</route>
----

YAML::
+
[source,yaml]
----
- route:
    from:
      uri: jgroups-raft:clusterName
      parameters:
        enableRoleChangeEvents: true
      steps:
        - to:
            uri: seda:queue
----
====

Using `jgroups-raft` component on the producer side of the route will use the body of the camel exchange
to perform a setX() operation on the raftHandle associated with the endpoint. The body is converted to a `byte[]`
(such as from text, a stream or a file). A body that cannot be converted, such as a `Map`, a `List`, a number or a POJO,
fails the exchange with an `InvalidPayloadException`. A null body is skipped: nothing is set.

[tabs]
====
Java::
+
[source,java]
----
from("direct:start").to("jgroups-raft:clusterName");
----

XML::
+
[source,xml]
----
<route>
  <from uri="direct:start"/>
  <to uri="jgroups-raft:clusterName"/>
</route>
----

YAML::
+
[source,yaml]
----
- route:
    from:
      uri: direct:start
      steps:
        - to:
            uri: jgroups-raft:clusterName
----
====

== Examples

=== Receive cluster view change notifications

The snippet below demonstrates how to create the consumer endpoint
listening to the change role events.
By default, this option is off.

[tabs]
====
Java::
+
[source,java]
----
from("jgroups-raft:clusterName?enableRoleChangeEvents=true")
    .to("mock:mockEndpoint");
----

XML::
+
[source,xml]
----
<route>
  <from uri="jgroups-raft:clusterName?enableRoleChangeEvents=true"/>
  <to uri="mock:mockEndpoint"/>
</route>
----

YAML::
+
[source,yaml]
----
- route:
    from:
      uri: jgroups-raft:clusterName
      parameters:
        enableRoleChangeEvents: true
      steps:
        - to:
            uri: mock:mockEndpoint
----
====

The role change is forwarded as a `LEADER` or `FOLLOWER` event. A `Learner` (a non-voting member that replicates the
log but cannot vote or become leader) is reported as a `FOLLOWER` event, so a route may receive consecutive `FOLLOWER`
events, for example when a node steps down from leader to learner and again when it becomes a voting follower.

=== Keeping singleton route within the cluster

The snippet below demonstrates how to keep the singleton consumer route
in the cluster of Camel Contexts. As soon as the master node dies, one
of the slaves will be elected as a new master and started. In this
particular example, we want to keep singleton xref:jetty-component.adoc[jetty]
instance listening for the requests on
address` http://localhost:8080/orders`.

._Java-only: programmatic JGroupsRaftClusterService configuration_
[source,java]
----
JGroupsRaftClusterService service = new JGroupsRaftClusterService();
service.setId("raftId");
service.setRaftId("raftId");
service.setJgroupsClusterName("clusterName");
...
context.addService(service);

from("master:mycluster:jetty:http://localhost:8080/orders").to("jms:orders");
----

NOTE: All the namespaces of a node share one Raft member: the `JGroupsRaftClusterService` connects one `RaftHandle`
(with the raft id of the service) for the cluster views of all namespaces. So the Raft leader is the leader of every
namespace, and the master routes of all namespaces run on that node. Raft does not elect a leader per namespace.
