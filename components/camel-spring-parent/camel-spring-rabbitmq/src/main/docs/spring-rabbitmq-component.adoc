:doctitle: Spring RabbitMQ

//Manually maintained attributes

*Since Camel {since}*

*{component-header}*

The Spring RabbitMQ component allows you to produce and consume messages from
http://www.rabbitmq.com/[RabbitMQ] instances. Using the Spring RabbitMQ
client.

Maven users will need to add the following dependency to their `pom.xml`
for this component:

[source,xml]
----
<dependency>
    <groupId>org.apache.camel</groupId>
    <artifactId>camel-spring-rabbitmq</artifactId>
    <version>x.x.x</version>
    <!-- use the same version as your Camel core version -->
</dependency>
----

== URI format

----
spring-rabbitmq:exchangeName?[options]
----

The exchange name determines the exchange to which the produced 
messages will be sent to. In the case of consumers, the exchange name 
determines the exchange the queue will be bound to.

== Usage

=== Using a connection factory

To connect to RabbitMQ, you need to set up a `ConnectionFactory` (same as with JMS) with the login details such as:

TIP: It is recommended to use `CachingConnectionFactory` from spring-rabbit as it comes with connection pooling out of the box.

[source,xml]
----
<bean id="rabbitConnectionFactory" class="org.springframework.amqp.rabbit.connection.CachingConnectionFactory">
  <property name="uri" value="amqp://localhost:5672"/>
</bean>
----

The `ConnectionFactory` is auto-detected by default, so you can do:

[tabs]
====
Java::
+
[source,java]
----
from("direct:cheese")
    .to("spring-rabbitmq:foo?routingKey=cheese");
----

XML::
+
[source,xml]
----
<camelContext>
  <route>
    <from uri="direct:cheese"/>
    <to uri="spring-rabbitmq:foo?routingKey=cheese"/>
  </route>
</camelContext>
----

YAML::
+
[source,yaml]
----
- route:
    from:
      uri: direct:cheese
      steps:
        - to:
            uri: spring-rabbitmq:foo
            parameters:
              routingKey: cheese
----
====

=== Noticing a dead or silent broker

How soon a route notices a broker that stopped answering without closing the connection (the host is gone, or a
firewall or NAT drops the packets) depends on the connection factory. The durations below describe how Spring AMQP and
the RabbitMQ Java client behave by default, approximately; they are not guarantees of Camel.

*Publisher confirms.* Without publisher confirms, the producer hands the message to the client and reports success:
on a silent or reset connection the send succeeds and the message can be lost without an error. Configure the
connection factory with simple publisher confirms. With the default `confirm=auto` the producer then waits up to
`confirmTimeout` (5 seconds) for RabbitMQ to confirm each message sent InOnly, and the send fails when it is not
confirmed, so the error handler can redeliver it. `confirm=enabled` waits the same way, and needs the connection factory
to have publisher confirms.

*Heartbeat.* The RabbitMQ Java client notices a silent connection through the heartbeat, 60 seconds by default (the
lower of the values that the client and the broker request). It reads with a timeout of a quarter of the heartbeat and
closes the connection after more than 8 such timeouts in a row: about 2.25 × the heartbeat, so about 135 seconds by
default. Until then a consumer receives nothing and logs no error. A lower heartbeat notices it sooner, for example
about 34 seconds with 15 seconds.

*Channel operations.* An operation that waits for an answer of the broker on a channel, such as opening a channel or
cancelling a consumer when the route stops, waits until the connection is closed or for up to the `channelRpcTimeout`
of the client, 10 minutes by default.

[source,xml]
----
<bean id="rabbitConnectionFactory" class="org.springframework.amqp.rabbit.connection.CachingConnectionFactory">
  <property name="uri" value="amqp://localhost:5672"/>
  <property name="publisherConfirmType" value="SIMPLE"/>
  <property name="requestedHeartBeat" value="15"/>
</bean>
----

In Java, `connectionFactory.getRabbitConnectionFactory().setChannelRpcTimeout(30000)` sets the channel timeout. With
Spring Boot:

[source,properties]
----
spring.rabbitmq.publisher-confirm-type=simple
spring.rabbitmq.requested-heartbeat=15s
spring.rabbitmq.channel-rpc-timeout=30s
----

After the connection breaks, the broker requeues the messages that the consumer received but did not acknowledge,
while the consumer may still process the ones it had already received: expect duplicates after a reconnect, up to
`prefetchCount` (250 by default) per consumer. Make the processing idempotent, or lower `prefetchCount`.

*Suspending or stopping a route.* The consumer stops its listener container, which cancels its consumers and waits
for the broker to answer, then waits up to its `shutdownTimeout` (the `shutdownTimeout` of the component, 5 seconds by
default, unless a custom `listenerContainerFactory` sets another one) for the messages that the route is still
processing. A route that suspends its own consumer, such as with a route policy when an exchange is done, waits that
whole `shutdownTimeout`, as the listener container waits for the message that the route is processing; the listener
container then closes the channel of that message, so the broker delivers it again once the route is resumed (unless
it was acknowledged on delivery, with `acknowledgeMode=NONE`). The consumer waits for the listener container to stop
at most the `shutdownTimeout` of the component plus the `shutdownAwaitTermination` of the `ExecutorServiceManager` (10
seconds by default), so that a broker that does not answer the cancel does not hold up the
xref:manual::graceful-shutdown.adoc[graceful shutdown]. When that time elapses, the consumer logs a WARN with the
endpoint and its queues, and returns: the listener container goes on stopping in the background, and is destroyed once
the cancel returns. When the route is resumed or started again, the consumer creates a new listener container.

=== Auto declare exchanges, queues and bindings

Before you can send or receive messages from RabbitMQ, then exchanges, queues and bindings must be setup first.

Since Camel 4.5, a consumer declares them when it starts, as `autoDeclare` is `true` by default: the exchange, of the
`exchangeType` (`direct` by default), the queues, and the binding between the exchange, the queues and the routing key.
A producer declares them only with `autoDeclareProducer=true`.

If the broker already has one of these elements with other settings, such as an exchange of another type or a queue
with other arguments, the broker refuses the declaration with `PRECONDITION_FAILED` and the consumer fails to start.
Configure the endpoint with the settings of the existing elements, or turn the declaration off with `autoDeclare=false`
(on the endpoint or the component), or for some elements with `skipDeclareExchange`, `skipDeclareQueue` or
`skipBindQueue`.

The consumer declares them again each time the connection factory opens a new connection, for example after the
connection to RabbitMQ was lost: a queue that RabbitMQ deleted meanwhile, such as an auto-delete or exclusive queue, is
declared again when the consumer reconnects.

When RabbitMQ is not available when the consumer starts, the consumer logs a warning and starts anyway: the listener
container keeps trying to connect, and the exchange, queue and binding are declared when it connects.
To fail the start instead, set `testConnectionOnStartup=true`.

NOTE: With a `CachingConnectionFactory` whose cache mode is `CONNECTION`, the consumer declares only when it starts, as
Spring's `RabbitAdmin`, and fails to start when RabbitMQ is not available.

The elements can be configured using the multivalued `args` option.

For example, to specify the queue as exclusive, you can configure the endpoint uri with `arg.queue.exclusive=true`.

*Exchanges*

[width="100%",cols="10%,10%,70%,10%",options="header",]
|=====================================================================
|Option |Type |Description|Default
| autoDelete | boolean | True if the server should delete the exchange when it is no longer in use (if all bindings are deleted). | false
| durable | boolean | A durable exchange will survive a server restart. | true
|=====================================================================

You can also configure any additional `x-` arguments.
See details in the RabbitMQ documentation.


*Queues*

[width="100%",cols="10%,10%,70%,10%",options="header",]
|=====================================================================
|Option |Type |Description|Default
| autoDelete | boolean | True if the server should delete the queue when it is no longer in use (queue that has had at least one consumer is deleted when last consumer unsubscribes). | false
| durable | boolean | A durable queue will survive a server restart. | true
| exclusive | boolean | Whether the queue is exclusive | false
| x-dead-letter-exchange | String | The name of the dead letter exchange. If none configured, then the component configured value is used. |
| x-dead-letter-routing-key | String | The routing key for the dead letter exchange. If none configured, then the component configured value is used. |
|=====================================================================

You can also configure any additional `x-` arguments, such as the message time to live, via `x-message-ttl`, and many others.
See details in the RabbitMQ documentation.

=== Mapping from Camel to RabbitMQ

The message body is mapped from Camel Message body to a `byte[]` which is the type that RabbitMQ uses for message body.
Camel will use its type converter to convert the message body to a byte array.

Spring Rabbit comes out of the box with support for mapping Java serialized objects, but Camel Spring RabbitMQ
does *not* support this due to security vulnerabilities and using Java objects is a bad design as it enforces strong coupling.

Custom message headers are mapped from Camel Message headers to RabbitMQ headers.
This behaviour can be customized by configuring
a new implementation of `HeaderFilterStrategy` on the Camel component.

The content type of a sent message is taken from the `CamelSpringRabbitmqContentType` header when it is set,
otherwise it is derived from the message body (`text/plain` for a `String`, `application/octet-stream` for other bodies).
The consumer sets this header to the content type of the consumed message, so a route that forwards a consumed message
to another queue keeps that content type. When the route changes the type of the body, such as turning a text message
into a byte array, remove the header before sending, otherwise the receiver reads the body with the content type of the
original message (a byte array sent as `text/plain` is received as a `String`):

[tabs]
====
Java::
+
[source,java]
----
from("spring-rabbitmq:orders?queues=incoming")
    .convertBodyTo(byte[].class)
    .removeHeader("CamelSpringRabbitmqContentType")
    .to("spring-rabbitmq:orders?routingKey=binary");
----

XML::
+
[source,xml]
----
<route>
  <from uri="spring-rabbitmq:orders?queues=incoming"/>
  <convertBodyTo type="byte[]"/>
  <removeHeader name="CamelSpringRabbitmqContentType"/>
  <to uri="spring-rabbitmq:orders?routingKey=binary"/>
</route>
----

YAML::
+
[source,yaml]
----
- route:
    from:
      uri: spring-rabbitmq:orders
      parameters:
        queues: incoming
      steps:
        - convertBodyTo:
            type: "byte[]"
        - removeHeader:
            name: CamelSpringRabbitmqContentType
        - to:
            uri: spring-rabbitmq:orders
            parameters:
              routingKey: binary
----
====

=== Request / Reply

Request and reply messaging is supported using https://www.rabbitmq.com/direct-reply-to.html[RabbitMQ direct reply-to].

The example below will do request/reply, where the message is sent via the cheese exchange name and routing key `foo.bar`,
which is being consumed by the second Camel route, that prepends the message with `Hello `, and then sends back the message.

So if we send `World` as message body to _direct:start_ then, we will se the message being logged

- `log:request -> World`
- `log:input -> World`
- `log:response -> Hello World`

._Java-only: Java DSL with ExchangePattern.InOut and body().prepend()_
[source,java]
----
from("direct:start")
    .to("log:request")
    .to(ExchangePattern.InOut, "spring-rabbitmq:cheese?routingKey=foo.bar")
    .to("log:response");

from("spring-rabbitmq:cheese?queues=myqueue&routingKey=foo.bar")
    .to("log:input")
    .transform(body().prepend("Hello "));
----

The consumer sets the `CamelSpringRabbitmqContentType` header to the content type of the request.
When the route leaves this header unchanged, the reply inherits the content type of the request depending on the reply body:

* A `String` reply keeps it, so a JSON `String` reply to an `application/json` request is sent as `application/json`.
* A byte array or stream reply (such as the output of `marshal`) keeps it, unless it is a text content type such as `text/plain`.
  Then the reply is sent as `application/octet-stream`, so a byte array reply to a text request is received as a byte array.
* Any other reply body does not keep it, and the message converter derives the content type from the reply body.

A content type the route sets in the `CamelSpringRabbitmqContentType` header, other than the one of the request, is always used.

When the route ends with a Spring AMQP `org.springframework.amqp.core.Message` as the body, that message is sent as the reply as it is.
If it has no correlation id, the correlation id of the request is set on it, so the requester can match the reply.

=== Reuse endpoint and send to different destinations computed at runtime

If you need to send messages to a lot of different RabbitMQ exchanges, it
makes sense to reuse an endpoint and specify the real destination in
a message header. This allows Camel to reuse the same endpoint, but send
to different exchanges. This greatly reduces the number of endpoints
created and economizes on memory and thread resources.

TIP: Using xref:eips:toD-eip.adoc[toD] is easier than specifying the dynamic destination with headers

You can specify using the following headers:

[width="100%",cols="10%,10%,80%",options="header",]
|=====================================================================
|Header |Type |Description
|`CamelSpringRabbitmqExchangeOverrideName` |`String` |The exchange name.
|`CamelSpringRabbitmqRoutingOverrideKey` |`String` |The routing key.
|=====================================================================

For example, the following route shows how you can compute a destination
at run time and use it to override the exchange appearing in the endpoint
URL:

[tabs]
====
Java::
+
[source,java]
----
from("file://inbox")
    .to("bean:computeDestination")
    .to("spring-rabbitmq:dummy");
----

XML::
+
[source,xml]
----
<route>
  <from uri="file:inbox"/>
  <to uri="bean:computeDestination"/>
  <to uri="spring-rabbitmq:dummy"/>
</route>
----

YAML::
+
[source,yaml]
----
- route:
    from:
      uri: file:inbox
      steps:
        - to:
            uri: bean:computeDestination
        - to:
            uri: spring-rabbitmq:dummy
----
====

The exchange name, `dummy`, is just a placeholder. It must be provided as
part of the RabbitMQ endpoint URL, but it will be ignored in this example.

In the `computeDestination` bean, specify the real destination by
setting the `CamelSpringRabbitmqExchangeOverrideName` header as follows:

._Java-only: Java handler method_
[source,java]
----
public void setExchangeHeader(Exchange exchange) {
   String region = ....
   exchange.getIn().setHeader("CamelSpringRabbitmqExchangeOverrideName", "order-" + region);
}
----

Then Camel will read this header and use it as the exchange name instead
of the one configured on the endpoint. So, in this example Camel sends
the message to `spring-rabbitmq:order-emea`, assuming the `region` value was `emea`.

Keep in mind that the producer removes both `CamelSpringRabbitmqExchangeOverrideName` and `CamelSpringRabbitmqRoutingOverrideKey`
headers from the exchange and do not propagate them to the created Rabbitmq
message to avoid the accidental loops
in the routes (in scenarios when the message will be forwarded to
another RabbitMQ endpoint).

=== Using toD

If you need to send messages to a lot of different exchanges, it
makes sense to reuse an endpoint and specify the dynamic destinations
with simple language using xref:eips:toD-eip.adoc[toD].

For example, suppose you need to send messages to exchanges with order types,
then using toD could, for example, be done as follows:

[tabs]
====
Java::
+
[source,java]
----
from("direct:order")
  .toD("spring-rabbit:order-${header.orderType}");
----

XML::
+
[source,xml]
----
<route>
  <from uri="direct:order"/>
  <toD uri="spring-rabbit:order-${header.orderType}"/>
</route>
----

YAML::
+
[source,yaml]
----
- route:
    from:
      uri: direct:order
      steps:
        - toD:
            uri: "spring-rabbit:order-${header.orderType}"
----
====

=== Manual Acknowledgement

If we need to manually acknowledge a message for some use case, we can
do it by setting and acknowledgeMode to Manual and using the below snippet
of code to get Channel and deliveryTag to manually acknowledge the message:

._Java-only: inline Processor with Spring RabbitMQ API_
[source,java]
----
from("spring-rabbitmq:%s?queues=%s&acknowledgeMode=MANUAL")
    .process(exchange -> {
        Channel channel = exchange.getProperty(SpringRabbitMQConstants.CHANNEL, Channel.class);
        long deliveryTag = exchange.getMessage().getHeader(SpringRabbitMQConstants.DELIVERY_TAG, long.class);
        channel.basicAck(deliveryTag, false);
    })
----
