= Apache Camel 4.x Upgrade Guide

This document is for helping you upgrade your Apache Camel application
from Camel 4.x to 4.y. For example, if you are upgrading Camel 4.0 to 4.2, then you should follow the guides
from both 4.0 to 4.1 and 4.1 to 4.2.

[NOTE]
====
https://github.com/apache/camel-upgrade-recipes/[The Camel Upgrade Recipes project] provides automated assistance for some common migration tasks.
Note that manual migration is still required.
See the xref:camel-upgrade-recipes-tool.adoc[documentation] page for details.
====

== Upgrading Camel 4.23 to 4.24

=== camel-jbang - camel validate and camel overview report the same endpoints no route consumes

`camel validate source` and `camel overview` now use the same rules for a `direct:`, `seda:` or `disruptor:` endpoint
that a route sends to and no route consumes, so they report the same endpoints on the same project:

* `disruptor:` endpoints are checked too, and `camel overview` no longer treats `disruptor:q` as `seda:q` (they are
  different endpoints at runtime); `vm:` and `direct-vm:`, which do not exist in Camel 4, are no longer joined with
  `seda:` and `direct:`.
* `camel validate` counts a `poll` or `pollEnrich` as consuming its endpoint, and a `toD` without an expression, an
  `enrich` with a constant endpoint, a rest verb, and the dead letter channel of an error handler as sending to it.
  It reads the flows of an `Integration` resource, and stays quiet for a `Pipe`.
* `camel overview` stays quiet, as `camel validate` does, when a route consumes an endpoint only known at runtime
  (`+from: direct:{{name}}+`), and no longer reports a `to` whose uri holds an expression.

So `camel validate` can report an endpoint it did not report before.

=== camel-jpa, camel-hazelcast - an exchange marked rollback only is not consumed

When a route marks the exchange rollback only (for example with `markRollbackOnly()` or `markRollbackOnlyLast()`)
there is no exception on the exchange, and these consumers treated it as a success. The JPA consumer deleted the entity
(or called its `@Consumed` method) and committed the poll, and the transacted (`transacted=true`) Hazelcast SEDA
consumer committed its transaction, so the message was removed from the queue. Now a rollback only exchange is not
consumed: the JPA consumer leaves the entity in the table, so the next poll consumes it again, as long as it still
matches the query. With `transacted=false` the other entities of the poll are still consumed (without logging a WARN),
and so is what a `@PreConsumed` method changed before routing; with `transacted=true` the whole poll is rolled back,
as for a failed exchange. The Hazelcast SEDA consumer rolls back its transaction, so the message stays in the queue.

A message that the route marks rollback only every time was removed before, and is now consumed again at every poll
(JPA), or taken from the queue again at once, without a delay (transacted Hazelcast SEDA, as for a failed exchange).
Handle such a message in the route instead, for example by moving it aside, rather than marking it rollback only
every time.

=== camel-hashicorp-vault - properties without engine use the `secret` engine

A `hashicorp:` property without an engine, such as `{{hashicorp:mysecret}}` or `{{hashicorp:mysecret#field}}`, now
reads the secret from the `secret` engine. Before, it read from the engine of the `hashicorp:` property resolved
before it (or from a `null` engine), and `{{hashicorp:mysecret#field}}` always resolved to no value. Properties with
an engine, such as `{{hashicorp:secret:mysecret#field}}`, are not affected.

A `hashicorp:` property without an engine and with a version, such as `{{hashicorp:mysecret@2}}`, now reads version 2
of the secret `mysecret` in the `secret` engine. Before, the `@2` was kept as part of the secret name.

A `hashicorp:` property with a field of a secret that does not exist, such as `{{hashicorp:secret:missing#field}}`,
now resolves to no value, as it already did without a field, so its default value or an optional placeholder
(`{{?hashicorp:secret:missing#field}}`) applies. Before, without a default value, it failed with a
`NullPointerException`.

=== camel-report-maven-plugin - Java routes are read with the Java DSL parser

The `validate` and `route-coverage` goals read Java routes with the Java DSL parser of camel-java-io instead of
camel-route-parser (Roaster). XML routes are read as before. The parser reads every `configure()` method of a source
file, including those of a route builder created inside a test, so `validate` can find and validate endpoints it did
not see before. An endpoint uri that is only a method call, such as `from(inboxQueue())`, is not validated (it was
validated as a property placeholder without a component before); with `logUnparseable=true` it is logged.

=== camel-jbang - the route-parser plugin is removed

The `route-parser` plugin (`camel route-parser`) and its `camel-jbang-plugin-route-parser` artifact are removed. Use
`camel cmd route-structure MyRoute.java` instead: it prints the structure of the routes of a Java source, read
without compiling it, and of YAML and XML sources too. If you installed the plugin, remove it with
`camel plugin delete route-parser`.

=== camel-wasm - the endpoint runs WASI command modules (Breaking change)

The `wasm` endpoint now runs WASI Preview 1 command modules (the body is standard input, standard output becomes the
body, the exit code and standard error are in `CamelWasmExitCode` and `CamelWasmStderr`) and no longer supports the
custom `alloc`/`dealloc` and JSON message ABI. The URI path is now the module (`wasm:classpath:upper.wasm`); the
function name and the `module` option are removed, and a header reaches the module only when listed in
`environmentHeaders`. To migrate, turn the function into a program that reads standard input and writes standard
output, built for `wasm32-wasip1` (Rust) or with `GOOS=wasip1 GOARCH=wasm` (Go). The `wasm` language is unchanged.

The endpoint runs every exchange on a new instance of the module, so a module can no longer keep state from one
message to the next. The 4.23 note that a failed call discards the Wasm instance therefore now only applies to the
`wasm` expression.

The following API of `camel-wasm` is removed or changed with the old ABI:

* `WasmComponent.getModule()` and `setModule(String)`, and `WasmConfiguration.getModule()` and `setModule(String)`:
the module is the path of the endpoint URI, available as `WasmEndpoint.getModule()`.
* The `functionName` path parameter of the endpoint: the third argument of the `WasmEndpoint` constructor is now the
module.
* `WasmSupport.deserialize(byte[], Exchange)`.
* The constructor `WasmProducer(Endpoint, String, String)` is replaced by `WasmProducer(WasmEndpoint)`.

=== camel-vertx-http - a header with several values is sent as several headers

A message header whose value is a `java.util.Collection` or an object array (as the HTTP consumers map a request
header that occurs more than once) was sent as one HTTP header with the `toString()` of the value, for example
`[a, b]`. The producer now sends one HTTP header per value. A collection or an object array that is empty, or that
holds only null values, now sends no header (an empty List was sent as the header value `[]`).

Every other value is converted to one String and sent as one header as before: a String (also when it contains
commas), a `byte[]` and the other primitive arrays, a `Map`, and a Vert.x `JsonObject` or `JsonArray` (sent as JSON).
A route that needs the old single header can set the header to a String, for example with `String.valueOf(list)`.

=== camel-knative-http - a header with several values is sent as several headers

A message header whose value is a `java.util.Collection` or an object array (as the consumer maps a request header
that occurs more than once) is now sent as one HTTP header per value. The Knative HTTP producer sent it as one HTTP
header with the `toString()` of the value, for example `[a, b]`, and the reply of the consumer sent only its last
value. A collection or an object array that is empty, or that holds only null values, sends no header (the producer
sent an empty List as the header value `[]`).

Every other value is one header. A String is sent as before, also when it contains commas, and the reply still sends
no header for a blank String. A `byte[]` is now converted to a String with the type converter (the producer sent its
`toString()`, such as `[B@1dc9f5ad`, and the reply only its last byte as a number). The producer sends a `Map` and a
Vert.x `JsonObject` or `JsonArray` as before, as their `toString()` (JSON for the Vert.x types). The reply now does
the same: it sent only the last entry of a `Map` or `JsonObject` in the form `key=value`, and only the last element
of a `JsonArray`.

A route that needs the old single header of the producer can set the header to a String, for example with
`String.valueOf(list)`.
