= Camel CLI - Managing Integrations

Once your Camel integrations are running, the CLI provides comprehensive management and monitoring capabilities — from listing processes and tailing logs to tracing messages and checking health.

TIP: Prefer a visual dashboard over individual commands?
Just type `camel tui` — the plugin auto-installs on first use.
It shows routes, messages, health, traces, and more in a single terminal view.
See xref:camel-jbang-tui.adoc[Camel TUI] for details.

For looking deeper into a misbehaving integration -- captured errors, blocked messages, memory leaks, heap and thread dumps,
startup timing, SQL and Kafka -- see xref:camel-jbang-diagnostics.adoc[Diagnostics].

== Controlling local Camel integrations

List running integrations with `ps`:

[source,bash]
----
camel ps
  PID   NAME                             READY  STATUS    AGE
 61818  sample.camel.MyCamelApplica...   1/1   Running  26m38s
 62506  dude                             1/1   Running   4m34s
----

Stop by name or PID:

[source,bash]
----
camel stop dude
Shutting down Camel integration (PID: 62506)
----

`camel stop` waits until the integration has stopped, up to `--timeout` (60 seconds by default). When it has not
stopped in time, it exits with code `124`, and `--kill` stops it at once. Use `--no-wait` to return without waiting.

NOTE: The name is matched as a prefix — `camel stop d` stops all integrations starting with _d_.
To stop exactly one when names overlap (e.g., `dude` and `dude2`), use the PID or append `!`: `camel stop dude!`.
A PID must be a running Camel integration, and a name or PID that matches nothing exits with code `3`
(see xref:camel-jbang-exit-codes.adoc[Exit Codes and Output]).

Restart an integration (stop + re-launch):

[source,bash]
----
camel restart dude
Stopping Camel integration: dude (PID: 62506)
Restarted Camel integration: dude (PID: 63010)
Log: ~/.camel/63010.log
----

`camel restart` waits until the integration has stopped, and until the new one has started, and prints the log file
of the new integration (its output, the warnings and errors and what it prints otherwise, is in
`~/.camel/<pid>-run.log`). When the new integration stops right away, it prints the end of the log
and exits with code `1`; when it is still starting after `--timeout`, it exits with code `124` and leaves it running.

Stop all integrations (omit the name):

[source,bash]
----
camel stop
Shutting down Camel integration (PID: 61818)
Shutting down Camel integration (PID: 62506)
----

Most management commands support `--watch` for continuous full-screen output:

camel ps --watch

----

== Controlling Spring Boot and Quarkus integrations

By default, the CLI only manages integrations started with `camel run`.
To manage Spring Boot or Quarkus applications, add the CLI connector dependency.

Spring Boot:

[source,xml]
----
<dependency>
    <groupId>org.apache.camel.springboot</groupId>
    <artifactId>camel-cli-connector-starter</artifactId>
</dependency>
----

Quarkus:

[source,xml]
----
<dependency>
    <groupId>org.apache.camel.quarkus</groupId>
    <artifactId>camel-quarkus-cli-connector</artifactId>
</dependency>
----

== Running in background

Use `--background` to run an integration as a background process (Camel Main only):

[source,bash]
----
$ camel run chuck.yaml --background
Running Camel Main: chuck in background with PID: 80093 (waiting to startup)
Camel Main: chuck (state: Running)
Log: /home/user/.camel/80093.log
----

Use `camel ps` to list, `camel log` to tail output, and `camel stop` to shut down.

The command waits up to 60 seconds for the integration to start, and reports any errors before returning.
Set how long with `--background-wait`, such as `--background-wait=2m`, or do not wait with `--background-wait=false`.
An integration that fails to start prints its log and exits with `1`.
One that is still starting after the wait exits with `124`, and is left running.

The logging of the integration goes to `~/.camel/<pid>.log`, which `camel log` reads.
Its output goes to `~/.camel/<pid>-run.log`, which `camel stop` removes: the warnings and errors of the logging, and
what the integration prints otherwise, such as why it cannot start.

== Getting status

The `camel get` command (equivalent to `camel get context`) shows overall status:

[source,bash]
----
camel get
  PID   NAME    CAMEL   PLATFORM        PROFILE  READY  STATUS   RELOAD  AGE   ROUTE  MSG/S  TOTAL  FAIL  INFLIGHT  LAST  DELTA  SINCE-LAST
 42240  cheese  4.12.0  JBang v0.126.0  dev      1/1   Running       0  1m8s    2/2   1.01     65     0         0     0     -1     1s/1s/-
----

The _Since Last_ column shows three time-since values: started/completed/failed.
For example, `0s/0s/-` means the last started and completed message just happened with no failures yet.
Use `--remote` to break down TOTAL into remote/total pairs.

TIP: Use `camel get --watch` for continuous updates.

=== The state of one integration in one call

`camel status` shows one integration, with what `camel get route`, `camel get health`, `camel get error` and `camel log`
show, in one command. That is what an AI agent wants after it has run or changed an integration.

It starts with what is wrong, in a few words each: a route that is not started or has failed exchanges, a health check
that is down, a failed reload, or a heap that is nearly full (`Problems: none` when all is well). Then it shows:

* the state and uptime, the folder the integration was started from, and its files (the files of its routes, and the
  properties files it loaded)
* the exchanges, and the oldest inflight one with where it is now (when the inflight exchanges are listed, as in dev
  mode)
* each route with its counters, its file and line, and its last error
* the health checks that are down
* the HTTP server with its endpoints and management endpoints
* the last errors
* the reloads of dev mode, with the outcome of the last one
* the Java version, heap, threads and garbage collections of its JVM
* the end of its log

For example, as one JSON document:

[source,bash]
----
camel status cheese --json
----

With `--json` it prints one document: `problems` is an empty list when all is well, the routes have the fields of
`camel get route --json`, `uptime` is in millis, and the log records are newest first.

Without a name it shows the only integration that runs. `--log-lines` and `--errors` set how many log records and
errors to show (20 and 5 by default).

== Route status

See per-route statistics across all running integrations:

[source,bash]
----
camel get route
  PID   NAME      ID      FROM                        STATUS    AGE   TOTAL  FAILED  INFLIGHT  MEAN  MIN  MAX  SINCE-LAST
 61818  MyCamel   hello   timer://hello?period=2000   Running  29m2s    870       0         0     0    0   14     0s/0s/-
 63051  dude      java    timer://java?period=1000    Running    46s     46       0         0     0    0    9     0s/0s/-
----

Use `--remote` to break down TOTAL, FAILED and INFLIGHT into remote/total pairs: the exchanges that came from a remote
endpoint, such as Kafka or HTTP, of all the exchanges of the route. A route with a remote consumer has only remote
exchanges, and a route such as `direct:audit` has the remote exchanges of the routes that call it. The same works with
`camel get processor --remote` and `camel top route --remote`, and the JSON of these commands has the remote counters
as `remoteTotal`, `remoteFailed` and `remoteInflight`.

Use `--checksum` to show the xref:routes.adoc#_route_checksum_and_revision[checksum and revision] of each route. The
checksum is the same in every run while the route is not changed, so comparing it with an earlier run tells which routes
changed; the revision counts the times a reload changed the route since the integration started. The JSON output
(`--json`) always has them, as `checksum` and `revision`.

TIP: Run `camel get --help` to see all available sub-commands.

== Visualizing routes

Render a visual diagram of routes in a running integration:

[source,bash]
----
camel cmd route-diagram myApp
----

This prints a Unicode route diagram in the terminal. Use `--theme=ascii` for plain text,
or `--output=diagram.png --theme=light` to save as an image.
A route diagram draws the steps of each route. With `--errors`, its `onException` clauses are drawn as well, in a
frame of their own below its steps, with where its failures go.

You can also render diagrams directly from source files (no running process needed):

[source,bash]
----
camel cmd route-diagram my-route.yaml
----

Show how routes connect to each other and to external systems with the topology view:

[source,bash]
----
camel cmd route-topology myApp
camel cmd route-topology myApp --external
----

The `--external` flag includes external systems (Kafka, databases, etc.) as nodes in the graph.
With a `--theme`, the `--errors` flag also draws the error handling: the routes reached only while a failure is
handled (such as the target of a dead letter channel), in a frame of their own below the routes, with where their
failures come from. With `--external` as well, the external systems only they use are in the frame too.
Routes created by Kamelets are hidden, as they are an implementation detail of the Kamelet; use `--kamelets` to include them.
Both commands include live metrics by default — use `--metric=false` to disable.

TIP: The xref:camel-jbang-tui.adoc[Camel TUI] shows route diagrams and topology interactively.

== Starting and stopping routes

Stop all routes in an integration:

[source,bash]
----
camel cmd stop-route chuck
----

Start them again:

[source,bash]
----
camel cmd start-route chuck
----

Without a name, the command applies to all integrations: `camel cmd stop-route` / `camel cmd start-route`.

Target a specific route with `--id`:

[source,bash]
----
camel cmd start-route --id=route1
----

Scope to a specific integration by adding its name:

[source,bash]
----
camel cmd start-route bar --id=route1
----

TIP: Separate multiple IDs with commas: `--id=route1,hello`.

== Enabling and disabling EIPs

*Available since Camel 4.14*

Disable individual processors at runtime without changing source code.
List processors with `camel get processor`, then disable by id:

[source,bash]
----
camel cmd disable-processor --id=log1
----

Re-enable a specific processor or all at once:

[source,bash]
----
camel cmd enable-processor --id=log1
camel cmd enable-processor
----

TIP: Separate multiple IDs with commas: `--id=log1,log2,setBody2`.

== Semantic definitions and evaluation

The CLI can inspect and try the running application's
xref:next@components:languages:semantic-language.adoc[semantic definitions and experts].
The application must run Camel 4.23 or newer, include `camel-semantic` with the
`semantic-metadata`, `semantic-evaluate` and `semantic-audit` developer consoles, and have the local
CLI connector enabled.
These commands use the connector; enabling the HTTP console is unnecessary.

[source,bash]
----
camel semantic my-app
camel semantic get my-app
camel semantic get my-app --json
camel semantic get my-app --expert=guard
----

`camel semantic` defaults to `camel semantic get`. The text output uses tables listing
definition names, experts, operations, state selectors, result types and resolution
errors, followed by the registered experts. Each evaluation declares its own expert;
there is no default expert. Configuration and contract-resolution errors appear alongside
the affected definition or expert. `--expert`
shows one expert's operations, input and result semantics, and parameter contract.
Inspection does not perform inference. Use `--json` for machine-readable output.

Evaluate a named definition with a sample exchange:

[source,bash]
----
camel semantic eval my-app --evaluation=safe \
  --body='Please summarize this message' --header=subject=example \
  --variable=language=en --json
----

The definition's state selector reads the supplied body, headers and exchange-local
variables. Variables with repository prefixes such as `global:` are rejected. The
sample is evaluated directly; it is not sent through the application's routes.

Alternatively, invoke an expert operation directly. Use `semantic get --expert` to
find the operation names and parameters supported by that expert:

[source,bash]
----
camel semantic eval my-app --expert=guard --operation=detect \
  --input='Please summarize this message' --json
camel semantic eval my-app --expert=grader --operation=score \
  --input='Sample answer' --parameter='criteria=json:["poor","good","excellent"]' --json
----

Choose either a named evaluation or a direct expert call. Direct calls require
`--expert`, `--operation` and `--input`. Repeat `--header`, `--variable` or `--parameter`
for multiple entries; duplicate keys are rejected.

Values are text by default. Prefix a value with `json:` for a typed JSON value, for
example `--parameter=threshold=json:0.7`, `--variable=enabled=json:true`, or
`--input='json:["first","second"]'`. Use a JSON string to pass literal text beginning
with `json:` or `file:`. `--body=file:sample.txt` and `--input=file:sample.txt` read the
file as UTF-8 text.

For an expert accepting images, `--body=image:/path/picture.png` or
`--input=image:/path/picture.png` reads a local PNG, JPEG, GIF or WebP file. Before reading,
the CLI queries the selected expert's runtime metadata for its `maxImageBytes` limit.
It checks both the file size and the actual read, and checks inline images before submitting
an evaluation. Configure the limit on the expert bean; the OpenAI Decisions expert defaults
to 10 MB (10,000,000 bytes) per image before base64 encoding. Both the CLI and TUI use that
same configuration. Missing image support or limit metadata prevents local image loading;
no evaluation is submitted. Use a JSON string to pass a literal `image:` prefix.

Evaluation prints the value, available probability or probabilities, confidence,
provider metadata, elapsed milliseconds and any error. It invokes the configured
provider and may incur charges. `--evaluation-timeout` bounds runtime evaluation
(default and maximum: 50000 milliseconds). `--timeout` bounds the CLI's wait for the
reply (default: 60000 milliseconds). A CLI timeout removes its request and asks the
connector to cancel unfinished work. Provider interruption is cooperative; remote or
native inference may continue. Configure provider-specific request timeouts as well.

Semantic commands use readable text by default: expert operations include a parameter table,
evaluation results use labelled fields, and audit events show the record and captured interpretation
in separate sections. Add `--json` to any semantic command to receive the complete JSON response
for scripts.

All semantic commands accept an integration name or PID. With no name they select the only
running integration; ambiguous selection fails and lists the matching PIDs.
Known versions older than 4.23 fail immediately with exit code 3. If the runtime version
is unavailable, the CLI attempts the request and applies the normal timeout.
Each request has its own reply file, so concurrent commands do not consume each
other's results.

=== Semantic audit history

`camel semantic audit` reads retained evaluations and request outcomes from the configured reader.
Querying performs no inference and does not change capture configuration.

[source,bash]
----
camel semantic audit my-app
camel semantic audit my-app --category=evaluation --executing-route-id=assess --limit=20
camel semantic audit my-app --expert="team expert" --since=2026-10-10T08:00:00Z --json
camel semantic audit my-app --event-id=EVENT_ID --json
camel semantic audit my-app --case-event-id=EVENT_ID --max-records=200 --json
camel semantic audit my-app --event-ids=EVENT_1,EVENT_2 --max-records=200 --json
----

Tables separate typed Result from Execution and show captured route provenance and breadcrumb association.
Detail retains fractional Score values, captured labels and declared meanings. Missing interpretation is
shown explicitly; current definitions do not reconstruct old results. Stored input is available only when
capture was explicitly enabled. Detail responses label it as untrusted data. Lists omit input; case/export
output requires `--include-input` to include it. The full response is available with `--json`.

Pages are newest first, default 50 and maximum 200. Exact filters are `--category` (`evaluation` or `request`),
`--expert`, `--definition`, `--operation`, entry `--route-id`, `--executing-route-id`, `--exchange-id` and `--breadcrumb-id`.
`--since` is inclusive and `--until` is exclusive, using ISO-8601 event/completion timestamps with a UTC offset.
Together they select `[since, until)`; the lower bound must precede the upper bound.
`--result-type` selects `BOOLEAN`, `CHOICE`, `SCORE` or `CLASSIFICATION`. With that explicit type,
`--result-value` matches a Boolean (`true`/`false`), an exact Choice label or numeric Score equality;
`--result-label` tests Classification membership; `--score-min`/`--score-max` specify inclusive finite Score bounds.
Missing or omitted values do not match value predicates. These filters apply before pagination, to retained
records only. Use the returned `nextCursor` with the same filters and both time bounds.
Unsupported filters produce an error. `--event-id` is an exclusive detail selector and returns exit code 3
when the record is absent. Persisted legacy decision records remain retrievable by ID and bulk export.

Cases associate records within one reader by breadcrumb, exchange, invocation and supported batch/request
relationships. Association is not proven causality; completeness remains unknown. `--max-records` bounds
case and bulk responses to 1..1000 (default 200), with a 4 MiB response budget. Missing IDs, bounded retrieval,
cursor expiry and backend failures remain distinct. Backend failures return exit code 1 without partial success.

=== Semantic monitoring

`camel semantic monitoring` reads current cached measurements supplied by semantic metric producers.
It works independently of audit retention and JMX. It performs no inference or backend query.

[source,bash]
----
camel semantic monitoring my-app --json
camel semantic monitoring my-app --source=departmentMetrics
----

Producers supply meaning, units, bounded dimensions, observation times, counts, distributions and durations.
The response includes collection health, omitted sources and evicted series. The cache contains the latest
values only and is cleared on restart. Historical queries, comparisons, alerting and dashboards belong in
external monitoring systems. See xref:next@components:languages:semantic-language.adoc[Semantic evaluation]
for the measurement contract and Micrometer follow-up scope.

=== Semantic command output and exit codes

With `--json`, stdout contains exactly one JSON document. Inspection returns the
runtime metadata object, including empty `evaluations` and `experts` arrays when
nothing is published. Successful evaluations retain the runtime result fields.
Errors use `{"status":"error","code":N,"message":"..."}` and retain any runtime
result fields, such as `error` and `elapsedMillis`. Diagnostics go to stderr.

[cols="1,4",options="header"]
|===
| Exit code | Meaning
| 0 | Successful inspection, audit retrieval (including empty history) or evaluation, including a boolean result of `false`.
| 1 | The integration rejected the action, evaluation or audit query failed, or an audit cursor expired.
| 2 | Invalid command arguments or sample values.
| 3 | No matching integration, ambiguous selection, unavailable semantic tooling, expert operations or selected audit event.
| 4 | No reply before the CLI timeout.
| 70 | Unexpected local CLI error; stderr includes the stack trace.
|===

See xref:jbang-commands/camel-jbang-semantic-get.adoc[camel semantic get],
xref:jbang-commands/camel-jbang-semantic-eval.adoc[camel semantic eval] and
xref:jbang-commands/camel-jbang-semantic-audit.adoc[camel semantic audit]
for the complete option reference.

== Developer Console

Enable the web-based developer console with `--console`:

[source,bash]
----
camel run hello.java --console
----

The console is accessible at http://localhost:8080/q/dev and provides insights into routes,
performance, and EIP-level metrics. The endpoints support both HTTP GET and POST.

When running with xref:camel-jbang-running.adoc#_runtimes[another runtime], the console is served where
that runtime puts it:

[width="100%",cols="2,4,4",options="header"]
|===
| Runtime | `--console` | `--console --observe`
| jbang, Camel Main | `http://localhost:8080/q/dev` | `http://localhost:9876/q/dev` (on the management port)
| Spring Boot | `http://localhost:8080/actuator/camel` (the `camel` actuator endpoint) | `http://localhost:9876/observe/camel`
| Quarkus | `http://localhost:8080/q/camel/dev-console` | `http://localhost:8080/q/camel/dev-console`
|===

The console has no authentication, so it is meant for development only. `camel export --console` therefore
includes the console dependency in the exported project, but only enables it in `application-dev.properties`,
so the console is there when the project runs with the dev profile (`camel.main.profile=dev` with Camel Main,
`spring.profiles.active=dev` with Spring Boot, and `quarkus:dev` with Quarkus) and not in a production build.
With `camel export --profile=dev` the dev profile is flattened into `application.properties`, and so is the console.

GET with query parameters:

[source,bash]
----
curl -s -H "Accept: application/json" http://0.0.0.0:8080/q/dev/top/ | jq
----

POST with a JSON body (avoids URL length limits for large payloads):

[source,bash]
----
curl -s -X POST -H "Accept: application/json" -H "Content-Type: application/json" \
  -d '{"language":"simple","template":"${body}","body":"hello"}' \
  http://0.0.0.0:8080/q/dev/eval-language | jq
----

== OpenAPI Swagger UI

For integrations using the xref:manual::rest-dsl.adoc[REST DSL], you can browse the generated OpenAPI
document in Swagger UI (similar to Hawtio for JMX):

[source,bash]
----
camel run hello.java --openapi-ui
----

Swagger UI is served at http://localhost:8080/q/openapi. The OpenAPI JSON document is at
http://localhost:8080/q/openapi.json (configured automatically via `camel.rest.apiContextPath`).

You can combine this with REST routes defined in Java, YAML, or XML DSL. The flag also works on
`camel run --dev` and adds `camel-openapi-java` and `camel-platform-http-main` to the runtime
classpath when needed.

== Message history

*Available since Camel 4.17*

The `camel get history` command shows a step-by-step summary of the last completed message
— what each EIP did, with curated details at each step.

Example route that reads a file, splits by line, filters, calls HTTP, and logs:

._Java-only: route with split, filter, and HTTP call_
[source,java]
----
import org.apache.camel.builder.RouteBuilder;

public class foo extends RouteBuilder {

    @Override
    public void configure() throws Exception {
        from("file:inbox?noop=true")
            .log("Incoming file")
            .split(body().tokenize("\n"))
              .filter(body().contains("world"))
                .log("Stop the world")
                .stop()
              .end()
              .to("log:line")
            .end()
            .to("https://camel.apache.org/xxx?throwExceptionOnFailure=false")
            .to("log:after-http")
            .log("complete");
    }
}
----

=== Interactive mode

Use `camel get history --it` for an interactive step-through view (similar to `camel debug`),
showing full message details including headers and body. Press ENTER to advance, P+ENTER to go back.

TIP: Run `camel get history --help` for all options.

== Tailing logs

Tail logs from one, several, or all integrations:

NOTE: The `camel log` command is not supported in Spring Boot or Quarkus runtimes.

[source,bash]
----
camel log chuck
camel log bar,chuck
camel log
----

Highlight keywords with `--find` (repeatable) or filter lines with `--grep` (case-insensitive):

[source,bash]
----
camel log chuck --find=invoice --find=order
camel log chuck --grep=error
----

By default, `log` tails continuously. Use `--follow=false` to output matching lines and exit.

=== The log of the previous run

When an integration stops, its log is kept as the log of its previous run, like `kubectl logs --previous` in Kubernetes.
Use `--previous` to see why an integration stopped, such as one that failed to start:

[source,bash]
----
$ camel log chuck --previous
The previous run of chuck (pid 80093) ended at 2026-10-19 10:32:01 (2m3s ago) with exit code 70: Failed to create route: route1 ...
2026-10-19 10:32:00.912  INFO 80093 --- [           main] org.apache.camel.main.MainSupport   : Apache Camel (JBang) 4.24.0 is starting
...
----

The first line, on stderr, says which run it was and how it ended. The log follows on stdout.
A run that Ctrl+C or SIGTERM stopped ended with exit code 130 or 143 (`(SIGINT)` or `(SIGTERM)` follows the code): the
JVM exits with 128 and the number of the signal, as a shell and Kubernetes show it.
The options `--tail`, `--since`, `--grep`, `--find` and `--startup` work as they do for a running integration.
When you run `camel log` with the name of an integration that is not running, the error says how its previous run ended.

Each name keeps the log of its last run that ended, as `~/.camel/<name>-previous.log`.
The next run of that name that ends replaces it. Like Kubernetes, at most the last 10 MB of a log are kept.
An integration that was killed, or whose JVM crashed, leaves its log behind.
That log becomes the log of its previous run the next time you look one up.

The log is kept for every runtime: `jbang`, the default (also with `--background`), and the runtimes that run with
Maven (`--runtime=spring-boot`, `quarkus` or `main`, and `camel run pom.xml` of an existing project).
With `quarkus` and `spring-boot`, Maven runs the app in a process of its own, so the first line has no pid and no exit
code of the app: it says how Maven ended when it failed, such as `Maven ended with exit code 1`.
A run on a Maven runtime that was killed leaves its log behind as `~/.camel/<name>.log`. That log becomes the log of the
previous run when the next run of that name starts.

== Circuit breaker status

View the state of xref:components:eips:circuitBreaker-eip.adoc[Circuit Breakers]:

[source,bash]
----
camel get circuit-breaker
  PID   NAME  COMPONENT     ROUTE   ID               STATE      PENDING  SUCCESS  FAIL  REJECT  FALLBACK  TIMEOUT
 56033  mycb  resilience4j  route1  circuitBreaker1  HALF_OPEN        5        2     3       0         3        1
----

REJECT counts the calls the open breaker refused without calling the service, FALLBACK the calls
the `onFallback` answered (failed, timed out and rejected calls alike), and TIMEOUT the calls that hit
the configured timeout, which the breaker otherwise counts as plain failures. A BULKHEAD column with
the calls rejected by a full bulkhead is shown when a bulkhead is configured.

TIP: Use `camel get circuit-breaker --watch` for continuous updates.

== Chaos rules

With xref:next@components:others:chaos.adoc[camel-chaos] (`camel run --chaos`), turn on faults in a running integration
and see how its routes cope:

[source,bash]
----
camel cmd chaos-add --rule='endpoint=kafka:orders* error rate=0.3 until=1m'
camel get chaos
camel get chaos myapp --report
camel cmd chaos-clear
----

`chaos-add`, `chaos-change` and `chaos-remove` take the name or pid of the integration; without it they act on the
only integration that runs, or the only one with chaos switched on, and otherwise fail with the list of the running
integrations. `chaos-add` prints the rule in plain words too (`fail 30% of the sends to kafka:orders*, for 1 minute`),
and with `--dry-run` it adds nothing, and prints what the rule would hit now: the sends, polls, routes or steps, with
their route.
`camel cmd chaos-suggest` suggests rules to try per route from what the routes do (an HTTP call without a circuit
breaker, a dead letter channel, a hand-off over seda, an input from outside), the most worth trying first, each with
why and the `chaos-add` command that adds it, with an expectation of what should hold despite the faults.
`camel get chaos` lists the current rules with their id, version, state, matches and the faults that fired, and
`--report` shows the report: the verdict, the seed, every version of every rule, the counts per route, and what has
been tried per route (the kinds of fault, how it went, and what the suggestions offer that no rule tried yet). Chaos is for
development only: it stays off with profile `prod`, and the commands cannot switch it on.

=== Chaos explorations

An exploration is a time to try chaos rules in, which camel-chaos enforces: at its deadline the rules are removed,
whatever happens. In it, `camel cmd chaos-experiment` runs one experiment in one call. It adds the rules (one with an
expectation that decides the hypothesis), sends the messages of `--feed` as `camel cmd send` does, waits until the
expectations are decided (at most `--wait`), ends the experiment and prints what came of it:

[source,bash]
----
camel cmd chaos-explore-start --budget=10m --focus=refunds
camel cmd chaos-experiment --hypothesis='a failed refund is read again' \
    --rule='route=refunds error rate=every:5 expect=refunds:failed<=0 within=30s' \
    --feed=refunds --body=file:test/chaos/refunds-fails/ --repeat=20 --interval=200ms
camel cmd chaos-explore-finish
----

[source,text]
----
Experiment 1 FAIL  a failed refund is read again (r1, ended after 6s)
  expect refunds:failed<=0: unmet, 4 failed
  routes: refunds 16 completed, 4 failed
  traffic: 20 messages sent to direct://refunds in 4s
  waited 1s for the verdict; 9m51s left of the exploration
----

The verdict is `FAIL` when an expectation is unmet (exit code 1), `PASS` when all are met, and `INCONCLUSIVE` when the
wait was up before an expectation was decided. `--feed` takes the endpoint, or the id of the route, as the `feed:` line
of `chaos-suggest` has it. `camel get chaos --report` shows the exploration with its experiments.

The messages of `--feed` are sent to the endpoint the route starts from, so they reach a route that starts from
`direct`, `seda`, a stub (`camel run --stub=kafka`) or a broker. An experiment refuses a feed that cannot reach its
route, with the reason: a route that starts from a timer, scheduler, cron or quartz makes its own messages (leave
`--feed` out), and a route that starts from a component that only consumes cannot be fed this way. It also refuses a
feed whose route does not lead to a route of its expectations, as the experiment would say nothing: the route the feed
reaches, and the routes it sends to (over `direct`, `seda`, a broker, or HTTP to the integration's own server), must
include one, unless a route that makes its own messages, such as a timer, sends to it. For example `--feed=parked` for
`expect=refunds:failed<=0`:

[source,text]
----
ERROR: The feed goes to route parked, but not to route refunds of the expectations, so the experiment would say
nothing: feed refunds instead (its id as the feed)
----

A route that serves HTTP over the server of Camel (`platform-http`, or the REST DSL) is fed with HTTP requests to that
server, on localhost and its port, with the path and method of the route, `--body` as the request body and `--header`
as HTTP headers. They are sent while the experiment waits for its verdict, and its traffic counts the status codes the
clients got, so a hypothesis such as "a client gets a 503, not a 500" has its evidence:

[source,bash]
----
camel cmd chaos-experiment --hypothesis='a client of payment gets an error, nothing is lost' \
    --rule='route=payment error rate=every:4 until=30s expect=payment:failed<=0 within=20s' \
    --feed=payment --body='{"orderId": "O-1", "amount": 10}' --repeat=12 --interval=100..300
----

[source,text]
----
  traffic: 5 messages sent to POST http://localhost:8080/payment in 1s, answered 200 x4, 500 x1 (of 12: the experiment ended first)
----

For a path with a parameter, `--feed` is the path to call, with an optional method: `--feed='PUT /orders/42'`. An HTTP
server with its own address on this machine (netty-http, undertow, jetty) is fed at that address, called as localhost;
one on another host is not fed.

A route that starts from `file:<folder>` is fed with files: each message is written as a file into the folder the route
polls, named so the route takes it: `chaos-<time>.json`, numbered as `chaos-<time>-<n>.json` when the messages are
repeated, with the extension of its `include` or `antInclude` filter, else of the body. A `CamelFileName` in `--header` names the files instead.
With `--body=replay:` nothing is sent: the files the route took, which it moved to `.camel` (or the folder of its `move`
option), are put back into its folder under their own names, and again while the experiment runs, as the route takes
them, so a rule with a rate meets enough messages. The route moves them over the ones there, so an experiment that is
run again has the same messages. A route with `noop=true` never takes a file of
the same name again, so it cannot be replayed.

A feed to a remote system that is not stubbed, such as a Kafka broker, has a warning, as the messages go to that system:
use a local one (`camel infra run kafka`), or stub it. A broker that `camel infra run` started on this machine is such a
local one: when the input of the route is on it (its address, as the integration reports it, is on a port of a service
that `camel infra ps` lists), there is no warning, and the traffic says so:

[source,text]
----
  traffic: 6 messages sent to kafka://refunds?brokers=localhost:9092&groupId=shop (the local kafka from camel infra) in 199ms
----

A real broker tests what a stub cannot, such as a consumer that reads a failed message again or goes on without it.

`camel cmd chaos-explore` lets the AI of `camel ask` do it all: let there be chaos. It starts the exploration with the
budget, and the AI reads the suggestions, runs one experiment per call, reads each verdict, and goes on while there is
time. It asks nothing on the way, as starting the command is the consent, and it never changes the routes. When it is
done the exploration is finished, and its report and the journal of the experiments are printed (exit code 1 when an
experiment failed):

[source,bash]
----
camel cmd chaos-explore --budget=10m
camel cmd chaos-explore myApp --budget=1h --focus=refunds --api-type=anthropic
----

It saves what it found in the project: the report and the journal in `test/chaos/reports/explore-<time>.md` (and
`.json`), and each experiment that failed as a scenario, `test/chaos/explore-<time>-<n>.chaos`, which
`camel run * --chaos=<file>` or `camel cmd chaos-load` replays (`--no-save` leaves them out). Run the integration with
`--stub=remote`, so the experiments do not reach real systems. A route fed over HTTP or from
files cannot be fed by an experiment yet. MCP clients have the same playbook as the prompt `camel_chaos_explore`. See
xref:next@components:others:chaos.adoc#_an_exploration[An exploration] in the camel-chaos documentation.

=== Chaos scenarios

A scenario keeps the rules of an experiment in a file of the project, such as `test/chaos/outage.chaos`: one rule per line,
`#` comments, and an optional `seed=` line so it fails the same messages each time. The phases come from `from=` and
`until=` of its rules.

[source]
----
# the stock service is down for a minute, then slow
seed=42
endpoint=http:stock* error status=503 until=1m
endpoint=http:stock* delay duration=2s from=1m until=1m
endpoint=http:stock* error rate=0.01 expect=orders:50 within=3m
----

Start with it, or load it into an integration that runs (which removes the rules there are and starts a new report):

[source,bash]
----
camel run * --chaos=test/chaos/outage.chaos
camel cmd chaos-load test/chaos/outage.chaos
----

`camel run *` and `camel export` leave `.chaos` files out. A run with chaos ends with exit code 1 when the verdict is
FAIL, so a scenario can gate a pipeline; `--chaos-report` writes the report as JSON when the run ends:

[source,bash]
----
camel run * --chaos=test/chaos/outage.chaos --max-seconds=240 --chaos-report=target/chaos-report.json
----

Without an expectation (`expect=`) there is no verdict, and the run ends with exit code 0 and a line that says so. See
xref:next@components:others:chaos.adoc#_scenarios[Scenarios] and
xref:next@components:others:chaos.adoc#_chaos_in_a_pipeline[Chaos in a pipeline] in the camel-chaos documentation.

== Exchange sanitizer

With xref:next@components:others:sanitizer.adoc[camel-sanitizer] (`camel run --sanitizer`), a running integration
reports where the processors of its routes break the contract of `AsyncProcessor`, such as a callback called twice or a
processor that throws instead of calling its callback (rule R1), and warns about a step whose callback has not come
(still pending). With `camel.sanitizer.checks=callback,commit` it also reports where the commit of a consumer runs
twice, never, or with the outcome of another exchange (rule R2, which is on by default only in tests, as it costs more
per message):

[source,bash]
----
camel run * --sanitizer
camel run * --sanitizer --prop camel.sanitizer.checks=callback,commit
camel get sanitizer
camel get sanitizer myapp --report
----

`camel get sanitizer` lists the violations with their rule, kind, route, step, processor and exchange; `--report` shows
the counts per rule and per kind, the commits followed (with R2), each violation with its threads and stacks, and the
still pending warnings. The sanitizer is on with profile `dev`, the default of `camel run`, and never with profile
`prod`. The report holds ids, names, threads, stacks and the class and message of an exception, never bodies or headers
(an exception message can still carry message data).

== Using Jolokia and Hawtio

https://hawt.io/[Hawtio] provides a web console for inspecting Camel integrations via JMX,

Started Jolokia for PID 62506

camel hawtio dude

camel jolokia 62506 --stop
