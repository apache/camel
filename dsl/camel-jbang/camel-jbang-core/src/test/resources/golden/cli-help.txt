== camel --help
Apache Camel CLI
Usage: camel [-hV] [COMMAND]

Options:
  -h, --help     Display this help and exit
  -V, --version  Print version information and exit

Running:
    run         Run as local Camel integration
    dev         Run in dev mode with live reload
    stop        Shuts down running Camel integrations
    restart     Restarts running Camel integrations (stop + re-launch)
    ps          List running Camel integrations
    log         Tail logs from running Camel integrations
    shell       Interactive Camel CLI shell.
    script      Run Camel integration as shell script for terminal scripting

Monitoring:
    status      The state of a running Camel integration in one call: where it
                runs and its files, its routes, health, last errors and last
                reload, its JVM, and the end of its log
    get         Get status of Camel integrations (use get --help to see sub
                commands)
    top         Top status of Camel integrations (use top --help to see sub
                commands)
    trace       Tail message traces from running Camel integrations
    hawtio      Launch Hawtio web console
    jolokia     Attach Jolokia JVM Agent to a running Camel integration

Actions:
    cmd         Performs commands in the running Camel integrations, such as
                start/stop route, or change logging levels. (use cmd --help to
                see sub commands)
    bind        DEPRECATED: Bind source and sink Kamelets as a new Camel
                integration

Development:
    init        Creates a new Camel integration
    export      Export to other runtimes (Camel Main, Spring Boot, or Quarkus)
    debug       Debug local Camel integration
    eval        Evaluate Camel expressions and scripts (use transform --help to
                see sub commands)
    explain     Explain what a Camel route does using AI/LLM
    transform   Transform message or Camel routes (use transform --help to see
                sub commands)
    dirty       Check if there are dirty files from previous Camel runs that did
                not terminate gracefully
    doctor      Checks the environment and reports potential issues
    sbom        Generate a CycloneDX or SPDX SBOM for a specific project
    nano        Nano editor to edit file

Configuration:
    config      Get and set user configuration values (use config --help to see
                sub commands)
    dependency  Displays all Camel dependencies required to run (use dependency
                --help to see sub commands)
    version     Manage Camel versions (use version --help to see sub commands)
    update      Update Camel project
    wrapper     Install Camel wrapper scripts for version pinning
    completion  Generate completion script for bash/zsh
    plugin      Manage plugins that add sub-commands to this CLI

Catalog:
    catalog     List artifacts from Camel Catalog (use catalog --help to see sub
                commands)
    doc         Shows documentation for kamelet, component, EIP, and other Camel
                resources
    infra       List and Run external services for testing and prototyping

AI:
    ask         Ask a question about a running Camel application using AI
    harden      Suggest security hardening for Camel routes using AI/LLM
    overview    High-level overview of the integrations in a project, optionally
                explained by AI/LLM
    semantic    List semantic definitions and expert contracts

Exit Codes:
    0   Success
    1   Failed: the command ran, but the outcome is negative
    2   Usage error: invalid option or argument
    3   Not found: no such integration, route or service
   66   File not found: no such file or directory
   70   Internal error: an unexpected exception
  124   Timed out: no reply from the integration in time

== camel ask --help
Ask a question about a running Camel application using AI
Usage: camel ask [-h] [--url=<url>] [--api-type=<api-type>]
                  [--api-key=<api-key>] [--model=<model>] [--timeout=<timeout>]
                  [--name=<name>] [--max-iterations=<max-iterations>]
                  [--tools=<tools>] [--yes] [--show-tools] [--show-stats]
                  [--verbose] [<question>]

Options:
  -h, --help                Display this help and exit
      --url=<url>           LLM API endpoint URL. Auto-detected if not
                            specified. Also reads AZURE_OPENAI_ENDPOINT or
                            WATSONX_URL env vars
      --api-type=<api-type>
                            API type: 'ollama', 'openai', 'anthropic', or
                            'watsonx'. Valid values: ollama, openai, anthropic,
                            gemini, watsonx
      --api-key=<api-key>   API key. Also reads ANTHROPIC_API_KEY,
                            OPENAI_API_KEY, WATSONX_APIKEY, or LLM_API_KEY env
                            vars
      --model=<model>       Model to use. Default: the provider's default; with
                            Ollama the installed model best at tool calling,
                            such as qwen3.6
      --timeout=<timeout>   Timeout in seconds for LLM response
                            Default: 120
      --name=<name>         Name or PID of the Camel process. Auto-detected when
                            exactly one process is running
      --max-iterations=<max-iterations>
                            Maximum number of tool-calling rounds
                            Default: 25
      --tools=<tools>       The tools the model gets: core (a small set, for a
                            local model), full, or auto (core for a local model,
                            full for a hosted one). Valid values: auto, core,
                            full
                            Default: auto
      --yes                 Run the calls that ask first without asking: file
                            writes, messages to endpoints the integration does
                            not have, SQL that changes data, code expressions,
                            stopping the integration, and camel commands that
                            change something. For scripts, where there is no
                            terminal to ask on
      --show-tools          Show tool calls and results as they happen
      --show-stats          Show token usage and elapsed time after response
      --verbose             Print debug information: HTTP requests, responses,
                            and parsed results
  <question>                Question to ask (omit for interactive chat mode)

Examples:
  camel ask "what routes are running?"
  camel ask "why is my route failing?" --name=myApp
  camel ask "show me the route structure" --api-type=anthropic
  camel ask "are there any blocked exchanges?" --model=gpt-4
  camel ask                                   (interactive chat)

== camel bind --help
DEPRECATED: Bind source and sink Kamelets as a new Camel integration
Usage: camel bind [-h] --source=<source> [--step=<step>] --sink=<sink>
                   [--error-handler=<error-handler>] [--property=<property>]
                   [--output=<output>] <<file>>

Options:
  -h, --help                Display this help and exit
      --source=<source>     Source (from) such as a Kamelet or Camel endpoint
                            uri
      --step=<step>         Optional steps such as a Kamelet or Camel endpoint
                            uri
      --sink=<sink>         Sink (to) such as a Kamelet or Camel endpoint uri
      --error-handler=<error-handler>
                            Add error handler (none|log|sink:<endpoint>). Sink
                            endpoints are expected in the format
                            "[[apigroup/]version:]kind:[namespace/]name", plain
                            Camel URIs or Kamelet name.
      --property=<property>
                            Adds a pipe property in the form of
                            [source|sink|error-handler|step-<n>].<key>=<value>
                            where <n> is the step number starting from 1
      --output=<output>     Output format generated by this command (supports:
                            file, yaml, json).
                            Default: file
  <<file>>                  Name of binding file to be saved

== camel cmd --help
Performs commands in the running Camel integrations, such as start/stop route,
or change logging levels. (use cmd --help to see sub commands)
Usage: camel cmd [-h] [COMMAND]

Options:
  -h, --help  Display this help and exit

cmd commands:
    browse                Browse pending messages on endpoints
    chaos-add             Add chaos rules to a running integration (camel-chaos,
                          for development only)
    chaos-change          Change a chaos rule of a running integration
                          (camel-chaos, for development only)
    chaos-clear           Remove all chaos rules of running integrations
                          (camel-chaos, for development only)
    chaos-experiment      Run one chaos experiment in the exploration of a
                          running integration: add its rules, send its traffic,
                          wait for the verdict, and end it
    chaos-explore         Let there be chaos: an AI explores by itself how a
                          running integration copes with faults, for a time
                          budget, and reports what held and what broke
    chaos-explore-finish  Finish the chaos exploration of a running integration
                          before its deadline
    chaos-explore-start   Start a chaos exploration in a running integration: a
                          time to try chaos rules in, that camel-chaos enforces
    chaos-load            Load a chaos scenario into a running integration
                          (camel-chaos, for development only)
    chaos-remove          Remove a chaos rule of a running integration
                          (camel-chaos, for development only)
    chaos-suggest         Suggest chaos rules to try in a running integration,
                          per route (camel-chaos, for development only)

== camel cmd chaos-experiment --help
Run one chaos experiment in the exploration of a running integration: add its
rules, send its traffic, wait for the verdict, and end it
Usage: camel cmd chaos-experiment [-h] [--hypothesis=<hypothesis>]
                                   [--rule=<rule>] [--feed=<feed>]
                                   [--body=<body>] [--header=<header>]
                                   [--repeat=<repeat>] [--interval=<interval>]
                                   [--wait=<wait>] [--note=<note>] [--end]
                                   [--timeout=<timeout>] [<name>]

Options:
  -h, --help                Display this help and exit
      --hypothesis=<hypothesis>
                            What the experiment tests, in a few words, such as
                            'orders survive a payment outage'
      --rule=<rule>         A rule in its one-line text form, as an entry of
                            camel.chaos.rules; can be given more than once, and
                            one of them needs an expectation (expect=)
      --feed=<feed>         The endpoint, or the id of the route, to send the
                            messages of the experiment to; a route that serves
                            HTTP gets HTTP requests, or give the path to call,
                            such as 'PUT /orders/42'
      --body=<body>         The body of the messages: text, file:<path>, or
                            file:<folder> for a message per file
      --header=<header>     A header of the messages as key=value; can be given
                            more than once
      --repeat=<repeat>     How many messages to send in all (at most 10000)
      --interval=<interval>
                            The pause between two messages, such as 200ms, or a
                            range such as 100..500 to draw each pause at random
                            (at most 60s)
      --wait=<wait>         The longest wait for the verdict after the messages
                            were sent, and at least the within= of the
                            expectations (at most 10m)
                            Default: 2m
      --note=<note>         What to note with the experiment when it ends
      --end                 End the open experiment (with --note) instead of
                            running a new one
      --timeout=<timeout>   How long to wait for the integration to answer, in
                            millis or as a duration such as 30s
                            Default: 10000
  <name>                    Name or pid of the running Camel integration (must
                            match one); without it, the only one running, or the
                            only one with chaos switched on

An experiment is part of an exploration (camel cmd chaos-explore-start). It
tests a hypothesis with rules, one of them with an expectation (expect=) that
decides it. The rules are added together, the messages of --feed are sent (as
camel cmd send sends them, with --body, --header, --repeat and --interval), and
then it waits until the expectations are decided, or --wait is up. The
experiment is ended then, its rules are removed, and what came of it is
printed: the verdict, the expectations, what the routes did, and the traffic. It
stays in the journal of the exploration (camel get chaos --report).

The verdict is FAIL when an expectation is unmet (exit code 1), PASS when all
are met, and INCONCLUSIVE when it cannot tell: it ended before an expectation
was decided (wait longer than the within= of the expectation), its faults never
fired, or the route of a met expectation had no messages. --feed can be the id
of a route, as the feed: line of camel cmd chaos-suggest has it.

Examples:
  camel cmd chaos-experiment --hypothesis='a failed refund is read again' \
      --rule='route=refunds error rate=every:5 expect=refunds:failed<=0 within=30s' \
      --feed=refunds --body=file:test/chaos/refunds-fails/ --repeat=20 --interval=200ms
  camel cmd chaos-experiment myApp --hypothesis='orders survive a payment outage' \
      --rule='endpoint=http:payment* error status=503 until=1m expect=orders:failed<=0 within=70s' \
      --wait=90s
  camel cmd chaos-experiment --end --note='stopped by hand'

== camel cmd chaos-suggest --help
Suggest chaos rules to try in a running integration, per route (camel-chaos, for
development only)
Usage: camel cmd chaos-suggest [-h] [--timeout=<timeout>] [<name>]

Options:
  -h, --help               Display this help and exit
      --timeout=<timeout>  How long to wait for the integration to answer, in
                           millis or as a duration such as 30s
                           Default: 10000
  <name>                   Name or pid of the running Camel integration (must
                           match one); without it, the only one running, or the
                           only one with chaos switched on

The rules come from what the routes do: an HTTP call without a circuit breaker
(the service answers with an error, or does not answer in time), a circuit
breaker (the service is down for a while), a call that the input may repeat
(Kafka, JMS: the call is made twice), a dead letter channel (it fails too), a
hand-off to another route over seda (the next route fails, and no message may
be lost between the two), an input from outside (the route fails at its entry,
the polls fail, the route stalls), and then two faults at once (an outage while
the dead letter channel fails, a slow service that also fails). The most worth
trying come first, each with why, the command that adds it, and how to feed the
route with messages (curl, a file, or camel cmd send), unless it feeds itself.
Nothing is added.

Without a name or pid, the only integration that runs, or the only one with
chaos switched on.

Examples:
  camel cmd chaos-suggest
  camel cmd chaos-suggest myApp
