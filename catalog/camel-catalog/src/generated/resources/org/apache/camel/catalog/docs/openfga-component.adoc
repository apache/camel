= OpenFGA Component
:doctitle: OpenFGA
:shortname: openfga
:artifactid: camel-openfga
:description: Authorize an Exchange against an OpenFGA relationship graph, and maintain the relationship tuples it is authorized against.
:since: 4.23
:supportlevel: Preview
:tabs-sync-option:
:component-header: Both producer and consumer are supported

*Since Camel {since}*

*{component-header}*

The OpenFGA component turns a Camel route into a Policy Enforcement Point (PEP) in front of
https://openfga.dev[OpenFGA], the CNCF authorization engine that implements Google's Zanzibar model. Where a
policy engine asks *what do the rules say*, OpenFGA answers a different question: *what is this subject's
relationship to this resource*.

That distinction is the reason the component exists. Expressing "anne may read `document:budget` because she owns
the folder it lives in" as policy-as-code means shipping the relationship graph into the policy input on every
message, which does not scale past a handful of relationships. OpenFGA keeps the graph — a set of
`(user, relation, object)` tuples — in the decision point, and the route asks it a question instead of handing it
data.

The component is a companion to `camel-opa` and
`camel-spiffe`, and deliberately shares camel-opa's shape and its security posture, so
that an operator who knows one knows the other:

[cols="1,3"]
|===
| `camel-spiffe` | establishes *who the caller is* (workload identity, X.509-SVID / JWT-SVID)
| `camel-opa` | evaluates *what the rules say* (policy-as-code, Rego)
| camel-openfga | answers *what the caller's relationship to the resource is* (ReBAC, relationship tuples)
|===

Maven users will need to add the following dependency to their `pom.xml`.

[source,xml]
------------------------------------------------------------
<dependency>
    <groupId>org.apache.camel</groupId>
    <artifactId>camel-openfga</artifactId>
    <version>x.x.x</version>
    <!-- use the same version as your Camel core version -->
</dependency>
------------------------------------------------------------

== Resolving the subject and the object

`user`, `object` and `relation` are evaluated as xref:languages:simple-language.adoc[Simple] expressions against
each Exchange, so a literal is used as written and an expression resolves per message:

[tabs]
====
Java::
+
[source,java]
------------------------------------------------------------
to("openfga:check"
        + "?storeId=01HQMVAJ..."
        + "&relation=reader"
        + "&user=user:${exchangeProperty.CamelKeycloakTokenSubject}"
        + "&object=document:${header.documentId}");
------------------------------------------------------------

YAML::
+
[source,yaml]
----
- route:
    from:
      uri: direct:checkDocument
      steps:
        - to:
            uri: openfga:check
            parameters:
              storeId: "01HQMVAJ..."
              relation: reader
              user: "user:${exchangeProperty.CamelKeycloakTokenSubject}"
              object: "document:${header.documentId}"
----
====

The component evaluates these itself, per Exchange, so a plain `to()` is enough — there is no need for `toD()` and
the endpoint cache it churns.

[IMPORTANT]
.Read the subject from an exchange property, not a header
====
An endpoint configured as `user=user:${header.userId}` lets the caller choose who to be — it is the
authorization-bypass equivalent of trusting a client-supplied username.

Put the subject where the caller cannot reach it. An exchange property set by the step in your route that
*verified* the caller cannot be set from outside the route, and a header usually can. Name that property here, and
let authentication decide who the caller is.

There is a convention worth following rather than inventing one: `camel-keycloak`'s `KeycloakSecurityPolicy` reads
the subject from the `CamelKeycloakTokenSubject` exchange property in preference to the header of the same name —
its `preferPropertyOverHeader` option defaults to `true`, for exactly the reason above. Nothing in Camel sets that
property for you, so the step in your route that validates the token is what has to record it; but recording it
under that name means the same identity serves both components.

Taking the **object** from a header is a different matter and is entirely normal: the caller is entitled to say
*which* resource it wants, and the check is what decides whether it may have it.
====

== Usage

=== As a producer, deciding with a filter

The `check` operation records the verdict in the `CamelOpenFgaAllowed` header and leaves the message body
untouched, so the route decides what to do with it:

[tabs]
====
Java::
+
[source,java]
------------------------------------------------------------
from("platform-http:/documents")
        .to("openfga:check?storeId={{fga.store}}&authorizationModelId={{fga.model}}"
            + "&relation=reader&user=user:${exchangeProperty.CamelKeycloakTokenSubject}"
            + "&object=document:${header.documentId}")
        .choice()
            .when(header("CamelOpenFgaAllowed").isEqualTo(true))
                .to("direct:serveDocument")
            .otherwise()
                .setHeader(Exchange.HTTP_RESPONSE_CODE, constant(403));
------------------------------------------------------------

YAML::
+
[source,yaml]
----
- route:
    from:
      uri: platform-http:/documents
      steps:
        - to:
            uri: openfga:check
            parameters:
              storeId: "{{fga.store}}"
              authorizationModelId: "{{fga.model}}"
              relation: reader
              user: "user:${exchangeProperty.CamelKeycloakTokenSubject}"
              object: "document:${header.documentId}"
        - choice:
            when:
              - expression:
                  simple:
                    expression: "${header.CamelOpenFgaAllowed} == true"
                steps:
                  - to:
                      uri: direct:serveDocument
            otherwise:
              steps:
                - setHeader:
                    name: CamelHttpResponseCode
                    expression:
                      constant:
                        expression: "403"
----
====

=== As a security policy, stopping the route

`OpenFgaSecurityPolicy` is an `AuthorizationPolicy`, so the check guards a section of the route and a denial throws
`CamelAuthorizationException` for the usual `onException` machinery to handle:

[tabs]
====
Java::
+
[source,java]
------------------------------------------------------------
OpenFgaSecurityPolicy policy = new OpenFgaSecurityPolicy();
policy.setApiUrl("http://openfga:8080");
policy.setStoreId("01HQMVAJ...");
policy.setAuthorizationModelId("01HQMVAK...");
policy.setRelation("writer");
policy.setUser("user:${exchangeProperty.CamelKeycloakTokenSubject}");
policy.setObject("document:${header.documentId}");

from("platform-http:/documents")
        .policy(policy)
        .to("direct:updateDocument");
------------------------------------------------------------

YAML::
+
[source,yaml]
----
- beans:
    - name: documentWriters
      type: org.apache.camel.component.openfga.security.OpenFgaSecurityPolicy
      properties:
        apiUrl: http://openfga:8080
        storeId: "01HQMVAJ..."
        authorizationModelId: "01HQMVAK..."
        relation: writer
        user: "user:${exchangeProperty.CamelKeycloakTokenSubject}"
        object: "document:${header.documentId}"
- route:
    from:
      uri: platform-http:/documents
      steps:
        - policy:
            ref: documentWriters
            steps:
              - to:
                  uri: direct:updateDocument
----
====

=== Filtering a collection

`batchCheck` takes the object identifiers from the body and replaces it with the ones the check allowed, in the
order the body asked in:

[source,java]
------------------------------------------------------------
from("direct:listDocuments")
        .to("sql:SELECT id FROM documents")
        // sql: answers with a List<Map>, one entry per row, so turn it into the object identifiers first - a Map
        // would stringify to {ID=budget}, which is not an identifier and would simply be skipped
        .process(exchange -> {
            List<Map<String, Object>> rows = exchange.getMessage().getBody(List.class);
            exchange.getMessage().setBody(rows.stream().map(row -> "document:" + row.get("id")).toList());
        })
        .to("openfga:batchCheck?storeId={{fga.store}}&relation=reader"
            + "&user=user:${exchangeProperty.CamelKeycloakTokenSubject}")
        .to("direct:render");
------------------------------------------------------------

The body comes back holding only the identifiers the check allowed, in the order it was given them.

By default, `batchCheckMode=client` sends one Check request per object, with at most `maxParallelRequests`
(default 10) in flight. This is compatible with older OpenFGA servers.

For OpenFGA 1.8.0 or later, set `batchCheckMode=server` to use the native BatchCheck API. The SDK groups checks into
HTTP requests containing at most `maxBatchSize` checks (default 50, configurable from 1 to 50; 50 is the default
per-request limit of an OpenFGA server, `max-checks-per-batch-check`, and the component does not go above it even
when a server is configured to accept more), and sends at most `maxParallelRequests` of those requests concurrently. Results are correlated back to their input positions, preserving
order and duplicate identifiers even when the server returns answers out of order. For example:

[source,java]
------------------------------------------------------------
.to("openfga:batchCheck?storeId={{fga.store}}&relation=reader&user=user:anne"
    + "&batchCheckMode=server&maxBatchSize=50&maxParallelRequests=2")
------------------------------------------------------------

The bounded wait accounts for the number of HTTP-request waves in the selected mode. An item error, an incomplete
response, or a failed request fails the entire filter, including when `failOpen=true`; server mode does not silently
fall back to client mode. SDK request retries remain governed by `maxRetries`.

`listObjects` answers the same question from the other end — ask OpenFGA which objects the subject can reach,
rather than filtering a list you already have:

[tabs]
====
Java::
+
[source,java]
------------------------------------------------------------
to("openfga:listObjects?storeId={{fga.store}}&relation=reader"
   + "&user=user:${exchangeProperty.CamelKeycloakTokenSubject}&type=document");
// body becomes [document:budget, document:roadmap]
------------------------------------------------------------

YAML::
+
[source,yaml]
----
- route:
    from:
      uri: direct:myDocuments
      steps:
        # the body becomes [document:budget, document:roadmap]
        - to:
            uri: openfga:listObjects
            parameters:
              storeId: "{{fga.store}}"
              relation: reader
              user: "user:${exchangeProperty.CamelKeycloakTokenSubject}"
              type: document
----
====

`listRelations` and `listUsers` round this out: what a subject may do with one object, and who may do something
with it. Both replace the body with a `List<String>`.

=== Streaming object queries

`streamedListObjects` uses OpenFGA's streamed object query and returns an
`OpenFgaObjectIterator`, implementing `Iterator<String>` and `java.io.Closeable`.
It opens the response lazily on first iteration and reads as the caller advances,
without collecting the full result list or adding a producer queue. A bounded
reader buffer provides pull backpressure. Ordinary `listObjects` still returns a
complete list; neither operation offers continuation-token pagination.

Use a streaming splitter to process each object incrementally:

[tabs]
====
Java::
+
[source,java]
----
from("direct:enumerate")
    .to("openfga:streamedListObjects?storeId={{fga.store}}"
        + "&authorizationModelId={{fga.model}}&relation=reader"
        + "&user=user:${exchangeProperty.subject}&type=document")
    .split(body()).streaming()
        .to("direct:processObject")
    .end();
----

YAML::
+
[source,yaml]
----
- route:
    from:
      uri: direct:enumerate
      steps:
        - to:
            uri: openfga:streamedListObjects
            parameters:
              storeId: "{{fga.store}}"
              authorizationModelId: "{{fga.model}}"
              relation: reader
              user: "user:${exchangeProperty.subject}"
              type: document
        - split:
            simple: "${body}"
            streaming: true
            steps:
              - to:
                  uri: direct:processObject
----
====

For `ProducerTemplate.requestBody`, consume the returned `OpenFgaObjectIterator`
in a try-with-resources block. It remains usable after the exchange completes.
Always close it when abandoning iteration. The streaming splitter closes a
`Closeable` iterator; exhaustion, failure and producer stop also close the response.

`isComplete()` becomes true only after iteration observes the end of the response.
Closing early leaves it false. Server errors, malformed records, timeouts and
connection errors throw from `hasNext()` or `next()`, including after earlier
objects have been delivered. Treat those earlier objects as partial results.
`failOpen` does not suppress streaming query failures. The component does not retry
this stream automatically, because replay could repeat objects already delivered.

`streamMaxResults` defaults to 10000 and fails iteration if another object arrives;
it never silently truncates the answer. `streamMaxLineLength` defaults to 65536
characters and bounds one JSON record. Both must be positive. `readTimeout` bounds
waiting for response headers and each blocking attempt to read the next record;
it does not limit time spent processing an object between calls. Closing the
iterator cancels an in-flight request and closes an active response body.

The operation preserves `authorizationModelId`, `consistency`, `conditionContext`
and configured contextual tuples. With the component-created client it uses the
SDK's authentication, serialization and TLS configuration. SDK 0.11 does not
expose a cancellable response-body handle from an injected `OpenFgaClient`.
Therefore an injected SDK client requires an explicit `streamingClient` implementing
`OpenFgaStreamingClient`, plus `storeId` and a positive `readTimeout`. This SPI must
return the actual cancellable request future and its closeable response body;
the application owns the SPI client's lifecycle. Endpoint credentials are not used
to guess the configuration of an injected SDK client.


=== Granting and revoking access

A route that creates a resource usually has to grant access to it too. `writeTuples` takes its tuple from the
endpoint's `user`/`relation`/`object` when they are configured, and from the body only when none of them is — the
configured tuple is the shape that reads best right after a resource was created:

[tabs]
====
Java::
+
[source,java]
------------------------------------------------------------
from("direct:createDocument")
        .to("sql:INSERT INTO documents ...")
        .to("openfga:writeTuples?storeId={{fga.store}}"
            + "&user=user:${exchangeProperty.CamelKeycloakTokenSubject}&relation=owner"
            + "&object=document:${header.documentId}");
------------------------------------------------------------

YAML::
+
[source,yaml]
----
- route:
    from:
      uri: direct:createDocument
      steps:
        - to:
            uri: "sql:INSERT INTO documents ..."
        - to:
            uri: openfga:writeTuples
            parameters:
              storeId: "{{fga.store}}"
              user: "user:${exchangeProperty.CamelKeycloakTokenSubject}"
              relation: owner
              object: "document:${header.documentId}"
----
====

For several tuples at once, leave `user`/`relation`/`object` unset and put them in the body instead — a collection of
`Map`s with `user`, `relation` and `object` entries, or of `ClientTupleKey` objects. `deleteTuples` accepts the same
shapes and revokes instead.

A `writeTuples` body may also set a relationship condition on a tuple: a `ClientTupleKey` built with `.condition(..)`,
or a `Map` whose `condition` entry is itself a map of a `name` and an optional `context`. The condition is written
through as given, so a conditioned grant stays conditioned; a tuple with no condition is written unconditioned. Because
a condition can ride only on the body, a tuple configured on the endpoint is always written without one; set the
condition on the body when you need a conditioned tuple. A `deleteTuples` body may carry a condition too, but it is
ignored, because OpenFGA deletes by identity.

[IMPORTANT]
.The endpoint wins over the body
====
If the endpoint configures any of `user`, `relation` or `object`, that is the tuple written and the body is not
consulted. The body is read only when the endpoint names none of them.

The same rule that governs a check governs a write: the configuration decides and the message does not. Were the body
preferred, a route that unmarshals an untrusted payload before writing would hand the caller the choice of which
relationship to grant — and `{"user": "user:attacker", "relation": "owner", "object": "document:secret"}` is a
perfectly well-formed tuple.

A partly configured triple is treated as a mistake rather than an invitation to fill the rest in from the message: the
producer fails and names the part that is missing.
====

A typed wildcard — `user:*`, OpenFGA's "everyone" — is accepted here, because writing that tuple is how a resource
is shared publicly and is a deliberate act by the route. It is *refused* as the subject of a check; see below.

=== Mutation conflicts and atomic updates

By default, `onDuplicate=error` makes an existing relationship fail a write, and `onMissing=error` makes an absent
relationship fail a delete. On OpenFGA 1.10.0 or later, select `onDuplicate=ignore` or `onMissing=ignore` explicitly
for reconciliation routes that should leave an already-satisfied operation unchanged. These options apply to
`writeTuples` and `deleteTuples`, respectively, and both apply to `write`.

Use `write` to grant and revoke relationships in one atomic request. With no configured `user`/`relation`/`object`,
the body is a Map containing `writes` and/or `deletes` collections. Each entry is an ordinary Map with `user`,
`relation` and `object`; a `timestamp` entry, as `readTuples` returns it, is ignored, so a page of `readTuples` can be
revoked as it is. A `condition` entry is written through on a write and ignored on a delete. Other body shapes or entry
fields are rejected. For example:

[source,java]
------------------------------------------------------------
Map<String, Object> changes = Map.of(
    "writes", List.of(Map.of("user", "user:anne", "relation", "writer", "object", "document:budget")),
    "deletes", List.of(Map.of("user", "user:anne", "relation", "reader", "object", "document:budget")));
template.requestBody("openfga:write?storeId={{fga.store}}&authorizationModelId={{fga.model}}", changes);
------------------------------------------------------------

The component requires at least one tuple and rejects an all-empty write, and the sum of writes and deletes cannot
exceed 100. It rejects larger transactions before calling OpenFGA and never splits this atomic update into
independently committed requests. A failed transaction remains a failure even when `failOpen=true`. The component
applies an endpoint-configured model revision to the transaction. A server configured with a lower tuple limit can
reject a request within the component's limit.

The configured-tuple precedence also applies to `write`: when any of `user`/`relation`/`object` is configured, that
triple supplies one write, the body is ignored, and no deletes are taken from it. A missing configured part fails
rather than falling back to the body.

Successful mutations preserve the input body. `CamelOpenFgaWrittenTuples` and `CamelOpenFgaDeletedTuples` report the
number of submitted operations, including any that the selected ignore mode skipped; they do not report the number of
rows changed in storage. The combined `write` operation sets both counters, including zero for an omitted side.

== Security

=== It fails closed

An OpenFGA server that cannot be reached, or that answers with an error, denies. The `failOpen` option reverses
that and is off by default; it is marked `insecure:dev` and should not be enabled in production.

`failOpen` covers only a *failure to obtain an answer*, and only for `check` and for `OpenFgaSecurityPolicy` — the
two places where "proceed" means something. It never turns a denial into an allow, and it never applies to an
Exchange that carried no usable subject (see below).

When `failOpen` does let an exchange through, it carries `CamelOpenFgaFailedOpen=true`. The verdict header alone
cannot distinguish "OpenFGA allowed this" from "OpenFGA was never reached and we were told to proceed", and an audit
asking which exchanges went through unauthorized needs something it can filter on. The marker is set only on that
deliberate path, and it is cleared on entry like the other decision headers so a sender cannot preload it.

It also does not apply when OpenFGA answers with an HTTP 4xx. A 400 means the question was malformed, a 401 or 403
that this client may not ask it, a 404 that what was asked about does not exist — none of which is a decision point
that has gone away. This matters concretely: an object identifier can get past the component's own guards and still
be rejected by the server (`document:a:b` and `document:x#y` are both HTTP 400 on OpenFGA 1.21.0), and if `failOpen`
covered that, any caller able to influence the identifier could turn a check into an allow. Those fail closed, and
the component logs why it did not fail open. A 429 is the one 4xx that does count as unavailable — it means "not
right now" — as do transport errors, timeouts and 5xx.

The rule is an allowlist rather than a list of exclusions: `failOpen` applies to a rate limit, a 5xx, a transport
error and a timeout, and to nothing else. A failure the component does not recognise — a request the SDK refused to
build, input it could not serialise, an interrupt during shutdown — is not evidence that OpenFGA was unreachable, so
it denies. Anything unfamiliar therefore fails closed rather than being waved through for being unfamiliar.

The query operations ignore `failOpen` entirely: a `batchCheck` or `listObjects` that failed has no safe way to
proceed, since handing back the objects it never managed to filter would be exactly the leak the filtering was there
to prevent.

=== What is asked is not up to the message

`storeId`, `authorizationModelId`, `relation` and the `operation` all come from the endpoint. An inbound message
cannot point the check at a different store, pin an older model revision, downgrade the relation demanded from
`owner` to `reader`, or turn a check into a tuple write.

The `CamelOpenFga*` headers are outputs only. They are cleared on entry — before the expressions are evaluated —
written on every evaluation, and never read back as inputs, so a verdict a message arrived with never survives into
the route, including down the paths that throw.

=== A missing identity is a denial, not a failure

If the `user` or `object` expression resolves to blank — or to a bare `user:` prefix, which is what a configured
prefix plus an unresolved expression leaves behind — the Exchange is denied with `CamelOpenFgaDenyReason` set to
`missing-user` or `missing-object`, and OpenFGA is never asked.

This split matters. OpenFGA would reject a blank subject with an HTTP 400, which is a *failure* to obtain a
verdict — and with `failOpen` set a failure becomes an allow. An Exchange that carried no identity has not been
authorized by anything, so it is denied, and `failOpen` does not reach it.

=== A wildcard subject is refused

`user:*` is a legitimate thing to write a tuple for. It is not a legitimate thing to *check*: asking "may everyone
read this" is not asking whether the caller may, and OpenFGA answers `true` for it wherever a public-access tuple
exists. A `user` expression that resolved to a typed wildcard would therefore hand out every publicly shared
object, so it is denied with `CamelOpenFgaDenyReason` set to `wildcard-subject`.

=== Pin the authorization model

`authorizationModelId` is optional, and leaving it out means "whichever model the store considers latest". A store
keeps every model it was ever given and "latest" moves the moment somebody writes a new one, so an unpinned
endpoint can start answering a different question than the one it was reviewed with — with no change to the route.
The component logs a warning at startup when it is unset. Pin it in production, so that a model rollout is a
deliberate, reviewable configuration change.

=== Consistency

OpenFGA's default read consistency may answer from a replica that has not caught up, which right after a revoke
means a deleted tuple can still grant access for a moment. Set `consistency=HIGHER_CONSISTENCY` on the paths where
that window matters, at the cost of latency.

The value is checked when the endpoint starts, and an unrecognised one — `higher_consistency`, say — is refused
rather than accepted and quietly sent as `unknown_default_open_api` on every request.

=== Authentication and TLS

For a server started with `--authn-method preshared`, set `apiToken`. For one behind an OIDC provider, set
`clientId`, `clientSecret`, `apiTokenIssuer` and `apiAudience` for the OAuth 2.0 client-credentials flow. Both
`apiToken` and `clientSecret` are marked secret and are masked wherever Camel prints an endpoint URI.

`sslContextParameters` configures TLS, including presenting a client certificate to a server that requires mutual
TLS. A SPIFFE X.509-SVID obtained through `camel-spiffe` works here, which closes the
loop: the workload authenticates to the authorization decision point as itself.

NOTE: `useGlobalSslContextParameters` on the component does not reach `OpenFgaSecurityPolicy`, which is a bean rather
than an endpoint of the component. Set `useGlobalSslContextParameters`, or `sslContextParameters`, on the policy itself.

=== Timeouts

`connectTimeout` and `readTimeout` bound the call, and `maxRetries` bounds how often a retryable failure is
re-attempted. The component supplies the SDK's HTTP client itself so that `connectTimeout` actually takes effect;
the SDK's own `connectTimeout` setting is accepted and then never read, and the client it builds by default sets
none, leaving the connect phase bounded only by the operating system.

== Health checks

Each check owns its HTTP client and releases it when the check stops. The five-second
health deadline includes the complete response body; a stalled body reports DOWN and
the outstanding request is cancelled.

Both the producer and `OpenFgaSecurityPolicy` register a readiness check that probes OpenFGA's `/healthz`
endpoint. Because the component fails closed, a route that is up but cannot reach OpenFGA fails every message, so
it is not ready — and this makes that visible before traffic arrives rather than only in the error logs afterwards.

The check requires the server to report `SERVING`, not merely to answer with HTTP 200: the HTTP gateway can answer
200 while the health service behind it reports `NOT_SERVING`.

No check is registered for an injected `openFgaClient`, which can point anywhere the component has no way to ask
about. Set `healthCheckProducerEnabled=false` on the component, or `healthCheckEnabled=false` on the policy, to
turn them off.

=== Contextual tuples and condition context

`contextualTuples` hands OpenFGA relationships that are true for one request and never stored — a group membership
that lives in the token rather than in the graph, or a fact about the request such as which network it arrived on.
It takes semicolon-separated `user,relation,object` triples, each part a Simple expression:

[tabs]
====
Java::
+
[source,java]
------------------------------------------------------------
// both the subject and the team come from exchange properties the route's own token-validating step set.
// the object may come from the request - asking about a document is the caller's prerogative - but the
// granting tuple must not, which is what the IMPORTANT block below is about
to("openfga:check?storeId={{fga.store}}&relation=reader"
   + "&user=user:${exchangeProperty.CamelKeycloakTokenSubject}"
   + "&object=document:${header.documentId}"
   + "&contextualTuples=user:${exchangeProperty.CamelKeycloakTokenSubject},member,"
   + "team:${exchangeProperty.tokenTeam}");
------------------------------------------------------------

YAML::
+
[source,yaml]
----
- route:
    from:
      uri: direct:checkWithTeam
      steps:
        - to:
            uri: openfga:check
            parameters:
              storeId: "{{fga.store}}"
              relation: reader
              user: "user:${exchangeProperty.CamelKeycloakTokenSubject}"
              object: "document:${header.documentId}"
              contextualTuples: "user:${exchangeProperty.CamelKeycloakTokenSubject},member,team:${exchangeProperty.tokenTeam}"
----
====

It applies to `check`, `batchCheck`, `listObjects`, `streamedListObjects`, `listRelations` and `listUsers`. On
`batchCheck` the context goes on *every* item in either client or server mode, so each object is judged against the
same facts.

`OpenFgaSecurityPolicy` takes both options as well, through `setContextualTuples` and `setConditionContext`. They are
no more dangerous on the policy than on an endpoint and no less: either way the value comes from whoever configured
the route, never from the message.

[NOTE]
.A comma inside a Simple expression
====
The option is split on `,` into its three parts *before* those parts are compiled, so a Simple expression containing
a comma — `${header.x.substring(0,3)}`, or a bean call with two arguments — breaks the triple. It cannot be
misinterpreted silently: the split yields either the wrong number of parts, or a part that is not a parsable
expression — `user:${bean:ids.pick(1,2)},member` splits into three and the first fails to compile with
`missing } to close the function` — so the route fails before it carries a message rather than checking something
other than what was written. Pre-compute such a value into an exchange property and reference that instead.
====

`conditionContext` supplies the values that any conditioned relation's CEL expression is evaluated with, as a map
resolved from the registry — `conditionContext=#myContext`. A map rather than an expression on purpose: OpenFGA types
every condition parameter in the authorization model (`int`, `bool`, `timestamp`, `ipaddress`), and a map lets you
supply the right Java type instead of a string the server would reject.

YAML, like a properties file, hands every value over as a string, the entries of a map included. OpenFGA converts a
string for an `int`, `uint`, `double`, `duration`, `timestamp` or `ipaddress` parameter, so those can be written as
they are, but it rejects one for a `bool` parameter: give that as `#valueAs(boolean):true`. A `list` or `map` parameter
cannot be written inline at all; declare it as a bean of its own and refer to it with `#bean:`:

[tabs]
====
Java::
+
[source,java]
------------------------------------------------------------
Map<String, Object> networkContext = Map.of(
        "trusted", true,
        "allowed_regions", List.of("eu", "us"));
context.getRegistry().bind("networkContext", networkContext);

from("direct:checkFromTrustedNetwork")
    .to("openfga:check?storeId={{fga.store}}&relation=reader"
        + "&user=user:${exchangeProperty.CamelKeycloakTokenSubject}"
        + "&object=document:${header.documentId}&conditionContext=#networkContext");
------------------------------------------------------------

YAML::
+
[source,yaml]
----
- beans:
    - name: allowedRegions
      type: java.util.ArrayList
      properties:
        "0": eu
        "1": us
    - name: networkContext
      type: java.util.LinkedHashMap
      properties:
        # a bool parameter needs a boolean: the string "true" is rejected
        trusted: "#valueAs(boolean):true"
        # a list parameter needs a list
        allowed_regions: "#bean:allowedRegions"
- route:
    from:
      uri: direct:checkFromTrustedNetwork
      steps:
        - to:
            uri: openfga:check
            parameters:
              storeId: "{{fga.store}}"
              relation: reader
              user: "user:${exchangeProperty.CamelKeycloakTokenSubject}"
              object: "document:${header.documentId}"
              conditionContext: "#networkContext"
----
====

`OpenFgaSecurityPolicy` also takes the map inline, under the same rules:

[source,yaml]
----
- beans:
    - name: documentReaders
      type: org.apache.camel.component.openfga.security.OpenFgaSecurityPolicy
      properties:
        storeId: "{{fga.store}}"
        relation: reader
        user: "user:${exchangeProperty.CamelKeycloakTokenSubject}"
        object: "document:${header.documentId}"
        conditionContext:
          trusted: "#valueAs(boolean):true"
          max_amount: 100
----

A value of the wrong type fails the check with an HTTP 400 from OpenFGA, naming the parameter it could not convert.
That is an answer rather than an unavailable decision point, so the exchange is refused even when `failOpen` is set.

[IMPORTANT]
.A contextual tuple grants
====
A contextual tuple is read exactly like a stored one. `user:anne,owner,document:secret` makes
`check(user:anne, owner, document:secret)` answer **true** whatever the store contains — it is not a hint or a
filter, it is an assertion that the relationship holds.

That is why both options are endpoint-only and are never read from the message. A contextual tuple the caller could
choose would let it assert the very relationship being checked, which is the whole decision. The same reasoning
applies to a condition context, because a condition can decide a relation.

It follows that an expression here which reads an inbound header hands the caller that power anyway. Keep these
literal, or derive them from something the route established — the same rule as for `user`.

A part that resolves to blank denies the exchange with `CamelOpenFgaDenyReason=invalid-contextual-tuple` rather than
being dropped. Dropping it would be the safer direction arithmetically, since losing a tuple can only make the check
stricter, but it would silently answer a different question than the endpoint was configured to ask.
====

Contextual tuples supplied by the *message* are deliberately not supported. If you need them, the tuple has to come
from somewhere the caller cannot reach, which in practice means the endpoint.

=== Reading the graph

`readTuples` answers "what access exists", as opposed to `check`'s "may this subject do this". Here `user`, `relation`
and `object` are a *filter* rather than a subject, and the body comes back as a list of maps keyed `user`, `relation`,
`object` and `timestamp`, plus a `condition` map of `name` and `context` when the stored tuple has one — deliberately
the keys `writeTuples` and `deleteTuples` accept, so a route can revoke what it just read, or re-grant it with its
condition intact, without reshaping anything:

[tabs]
====
Java::
+
[source,java]
------------------------------------------------------------
from("direct:revokeEverythingBobHas")
        .to("openfga:readTuples?storeId={{fga.store}}&object=document:&user=user:bob")
        .to("openfga:deleteTuples?storeId={{fga.store}}");
------------------------------------------------------------

YAML::
+
[source,yaml]
----
- route:
    from:
      uri: direct:revokeEverythingBobHas
      steps:
        - to:
            uri: openfga:readTuples
            parameters:
              storeId: "{{fga.store}}"
              object: "document:"
              user: "user:bob"
        - to:
            uri: openfga:deleteTuples
            parameters:
              storeId: "{{fga.store}}"
----
====

[NOTE]
.What OpenFGA accepts as a read filter
====
The filter is narrower than "every part is optional". Measured against OpenFGA 1.21.0:

* no filter at all — reads the whole store, a page at a time;
* `object=document:` *plus* a `user` — reads that user's tuples of that object type;
* `object=document:budget` — reads that object's tuples, with or without a user or relation;
* `user` alone, `relation` alone, or `object=document:` alone — **rejected**, because OpenFGA requires an object type
  as soon as any filter is given and will not accept an empty object id and an empty user together.

The component checks this before the call and names the option to change, rather than letting an opaque HTTP 400
through. Note this is also why a type-only `document:` is accepted here but not as an `object` anywhere else: a read
filter and an identifier have different rules.

What "optional" does *not* mean is that a part may go missing at runtime. Only an option the endpoint never set counts
as "do not filter on this"; an option that *is* set and evaluates to nothing — `user=${header.who}` on a message with
no `who` header — is refused. Dropping it would make the read wider than the route asked for, and with the
`readTuples` -> `deleteTuples` route above that turns "revoke Bob's access" into "revoke everyone's". A filter that
silently widens when a value goes missing is the read-side form of failing open.
====

`readChanges` reads the change log, which is the building block for keeping a cache or a projection in step with the
graph. Each entry adds an `operation` of `WRITE` or `DELETE`, and carries the same `condition` map as `readTuples`
when the changed tuple has one.

Both are paged. `pageSize` bounds one request, and the token the page returns arrives on
`CamelOpenFgaContinuationToken`; feed it back through `continuationToken` to read on.

=== Consuming the change log with durable checkpoints

Only `readChanges` supports consumption. It polls one bounded page per scheduled
poll and sends a `List<Map<String, Object>>` containing the changes, in server
order, to the route. Configure `pageSize` to bound the requested page size; empty
tail pages do not produce exchanges. Standard scheduled polling options, such as
`delay`, `initialDelay` and polling backoff, control the schedule.

Register an application-provided `org.apache.camel.spi.StateRepository<String, String>`
as `changeCheckpoints`. A repository that is a Camel service, such as `FileStateRepository`,
is started by the consumer when the application has not started it, and stopped again when
the route stops; a repository the application started stays under the application's control.
A repository that several routes share, each with its own `checkpointKey`, should be started
and stopped by the application: otherwise the first route to start owns it and stops it with
that route, and a stopped `FileStateRepository` answers `null` to the other routes, which then
start again from `startTime` or the beginning:

[tabs]
====
Java::
+
[source,java]
----
from("openfga:readChanges?storeId={{fga.store}}&type=document"
    + "&checkpointRepository=#changeCheckpoints&checkpointKey=documents-projection-v1"
    + "&pageSize=100&delay=1000&changePollTimeout=30000")
    .split(body()).shareUnitOfWork().stopOnException()
        .to("direct:applyChange")
    .end();
----

YAML::
+
[source,yaml]
----
- route:
    from:
      uri: openfga:readChanges
      parameters:
        storeId: "{{fga.store}}"
        type: document
        checkpointRepository: "#changeCheckpoints"
        checkpointKey: documents-projection-v1
        pageSize: 100
        delay: 1000
        changePollTimeout: 30000
      steps:
        - split:
            expression:
              simple:
                expression: "${body}"
            shareUnitOfWork: true
            stopOnException: true
            steps:
              - to:
                  uri: direct:applyChange
----
====

Both `checkpointRepository` and `checkpointKey` are required. Implement the
repository with durable storage: `getState(key)` returns the last committed cursor
or null, and `setState(key, cursor)` must atomically persist it before returning.
A failed store must preserve the previous value. Repository methods must impose
finite I/O deadlines. Camel does not substitute an in-memory repository and does
not own the repository's lifecycle. Reuse a state repository only when it meets
these durability and failure requirements; an in-memory repository cannot resume
after a process restart.

Choose a stable key unique to the server, store, type filter and projection.
Exactly one active consumer may own a key; the SPI does not provide distributed
leader election. For clustered deployments, consider xref:master-component.adoc[master]
to run one active route. A component-level checkpoint key must still be unique
for every consumer. Use a different key when deliberately rebuilding a projection
or changing its filter. `continuationToken` is not accepted on a consumer;
the durable repository is its only cursor source. `startTime` applies only
before a cursor exists and must remain consistent across restarts.

After the whole page succeeds, the consumer durably stores its next token.
A route exception or rollback leaves the checkpoint unchanged. A handled route
exception counts as successful processing, so do not mark an incomplete
projection as handled. With a splitter, propagate failure to the parent page as
in the example. Avoid fire-and-forget processing when the checkpoint must cover
the resulting work.

Delivery is *at least once*. A crash after applying changes but before storing
the checkpoint, a failed checkpoint write, or shutdown during page processing can
repeat the complete page on the next poll or restart. Make projection updates
idempotent. The checkpoint and downstream side effects do not form one atomic
transaction. Ordering is preserved within each server page and between polls
of a single consumer; parallel route processing can change application order.

The repository is reloaded on each poll. An empty tail page retains an echoed
cursor, an advanced empty-page cursor is stored, and a missing token never erases
the existing bookmark. Read failures, including expired or invalid server cursors,
are reported through the polling error handler; they never silently restart at
the beginning. Cursor validity and retained history depend on the OpenFGA server
and its storage configuration. Plan recovery or a projection rebuild when the
server can no longer resume a bookmark; checkpoints cannot guarantee indefinite
replay.

`changePollTimeout` bounds awaiting the page request and cancels it on expiry.
Stopping the consumer cancels a pending request and prevents acknowledging an
unfinished page. SDK request timeouts still apply. Route processing and repository
calls must cooperate with Camel shutdown and their own deadlines; the consumer
does not forcibly interrupt arbitrary application code. `failOpen` does not
suppress polling or checkpoint failures.

The `readChanges` producer remains available for manual polling. Its caller owns
cursor persistence and must save the returned `CamelOpenFgaContinuationToken`
only after successfully processing the complete page. An exchange property or
global variable is not a durable checkpoint across restarts.

`startTime` bounds where a first read begins — without it a first `readChanges` on a busy store pages through the whole
history before reaching anything current.

[IMPORTANT]
.The two read operations signal "done" differently
====
Measured against OpenFGA 1.21.0, not assumed:

* `readTuples` returns no token on its last page, so `CamelOpenFgaContinuationToken` is **absent** once the read is
  finished. Looping until the header is missing is the right way to drain it.
* `readChanges` returns a token **every** time, including when nothing has happened — it hands the token you sent
  straight back with an empty page. Looping until the header is missing would therefore never end. The signal there is
  an **empty body**, and the token it keeps returning is the bookmark the next poll resumes from, which is why the
  component leaves it in place instead of clearing it.
====

`expand` is the odd one out: it is the only operation that does not leave a `List` on the body, because its answer is
a tree of usersets rather than a list. The `UsersetTree` goes on the body as the SDK returns it — flattening it is
exactly what would destroy the information the operation exists to provide. Reach for it when a check answered
something surprising and you need to see how it got there.

== What this component does not do yet

* Store and authorization-model management — `createStore`, `deleteStore`, `writeAuthorizationModel` and the rest.
  These are administrative rather than integration operations, and a component that can delete the store it
  authorizes against is a different proposition from one that can only ask it questions.

== Asynchronous authorization processing

`streamedListObjects` keeps its lazy iterator handoff inline, including when
`asyncProcessing=true`. It does not allocate authorization workers or apply an
`asyncTimeout` to the iterator's lifetime. The iterator's `readTimeout` and close
contract continue to govern each request and read.

Set `asyncProcessing=true` to release the invoking routing thread while the
component performs authorization or identity work. It defaults to false, preserving
existing scheduling. Synchronous `ProducerTemplate` calls remain usable and wait
for the same result and exception contract.

OpenFGA asynchronous processing uses SDK future callbacks for responses. Bounded workers only submit requests, including SDK authentication that may block while obtaining an OAuth token; workers never wait for response futures.

[source,java]
----
.to("openfga:check?storeId={{fga.store}}&relation=reader&user=user:${header.subject}&object=document:${header.documentId}&asyncProcessing=true&asyncPoolSize=4&asyncQueueSize=100&asyncTimeout=30000")
----

`asyncPoolSize` defaults to 4 and `asyncQueueSize` to 100; both must be positive.
The component also caps admitted invocations at their sum, including outstanding
SDK futures after the submission worker returns. Saturation rejects immediately
instead of running authorization on the routing thread. Executors are managed by
Camel and reused for the lifetime of the producer or wrapped policy processor;
none is created per exchange.

The authorization worker limit is enforced even with Camel's virtual-thread pool
factory. Cancelled blocking calls retain capacity until their SDK invocation
returns. Routing callbacks use a separate Camel-managed cached executor, independent of
`asyncPoolSize`, so a callback cannot occupy the deadline scheduler or limit
subsequent authorization work. Authorization admission is released when the decision
is committed, before invoking the callback. Downstream route concurrency follows
the route's own configuration. Each producer or wrapped policy uses one deadline
scheduler, and idle continuation workers expire through the cached executor.

The continuation executor has no admission limit. With platform threads, a blocking
downstream continuation can occupy one thread; with virtual threads, each continuation
uses a virtual thread. `asyncPoolSize` and `asyncQueueSize` bound authorization work,
not downstream thread or memory use. Configure downstream concurrency through the
route's consumer or concurrency controls when it needs a separate limit.

`asyncTimeout` defaults to 30000 milliseconds and must be positive. It covers
queueing, SDK invocation and authorization completion, not downstream route
processing. Expiry, rejection and shutdown fail closed and do not activate
`failOpen`. Backend availability errors still follow the
existing configured failed-open rules. Stopping cancels admitted work and returns
one callback per invocation. A late result cannot replace an interrupted or
cancelled invocation with an allow.

Inputs are captured per invocation before queueing, including Map/List container
snapshots. Snapshot processing does not complete the original exchange's unit of
work. Other body objects retain normal Camel object ownership rules. Policy
wrappers resume their guarded processors through Camel's asynchronous routing
engine after authorization succeeds.

Cancelling the future returned by a component producer's `processAsync` cancels
its admitted invocation. Interrupting that producer's synchronous facade also
cancels it and preserves the interrupt flag. Camel's own `ProducerTemplate` wait
or future cancellation has its framework lifecycle semantics and may stop waiting
without immediately cancelling the SDK request; the component deadline and stop
handling remain in effect. Cancelling an SDK future or interrupting a worker is a
best-effort transport cancellation: an SDK that ignores cancellation can keep its
bounded worker occupied until it returns, but cannot commit a late exchange result.

The OpenFGA security policy supports the same four options, for example
`openFgaPolicy.setAsyncProcessing(true)`. Every producer operation uses the future
bridge. Existing `connectTimeout`, `readTimeout`, `maxRetries` and the operation's
await budget still apply, including the batch fan-out budget. `asyncTimeout` is an
additional cap, including queue time; increase it when large batches require
multiple request waves. Cancellation propagation reaches the SDK's Java future;
closing the underlying HTTP response is subject to the SDK transport's support.
