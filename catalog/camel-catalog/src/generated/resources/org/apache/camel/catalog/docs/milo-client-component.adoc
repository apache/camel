*{component-header}*

The Milo Client component provides access to OPC UA servers using the
http://eclipse.org/milo[Eclipse Milo™] implementation.

*Java 11+*: This component requires Java 11+ at runtime.

NOTE: This component uses Eclipse Milo 1.0.5. When migrating from earlier versions,
be aware that the Milo API has undergone significant changes in the 1.0.x series.

Maven users will need to add the following dependency to their `pom.xml`
for this component:

[source,xml]
----
<dependency>
    <groupId>org.apache.camel</groupId>
    <artifactId>camel-milo</artifactId>
    <version>x.x.x</version>
    <!-- use the same version as your Camel core version -->
</dependency>
----


== URI format

The URI syntax of the endpoint is:

----
milo-client:opc.tcp://[user:password@]host:port/path/to/service?node=RAW(nsu=urn:foo:bar;s=item-1)
----

If the server does not use a path, then it is possible to simply omit it:

----
milo-client:opc.tcp://[user:password@]host:port?node=RAW(nsu=urn:foo:bar;s=item-1)
----

If no user credentials are provided the client will switch to anonymous mode.

As an alternative to URI-embedded credentials (`user:password`), you can provide
credentials explicitly using the endpoint parameters `username` and `password`.
This is recommended when credentials contain special characters (for example
`?`, `/`, `@`, `&`, `%`(%25)) that can make URI-embedded credentials difficult to handle.

For example:

----
milo-client:opc.tcp://host:port/path/to/service?node=RAW(nsu=urn:foo:bar;s=item-1)&username=RAW(my?user@name)&password=RAW(p@ss/w&rd)
----

When both styles are provided, the explicit `username`/`password` parameters take
precedence over credentials embedded in the URI.

All configuration options in the group +client+ are applicable to the shared client instance. Endpoints
will share client instances for each endpoint URI plus `requestedPublishingInterval`.
So the first time a request for that endpoint URI (plus `requestedPublishingInterval`) is made, the options of
the +client+ group are applied. All further instances will be ignored.

If you need alternate options for the same endpoint URI it is possible though to set the +clientId+ option
which will be added internally to the endpoint URI in order to select a different shared connection instance.
In other words, shared connections located by the combination of endpoint URI, `requestedPublishingInterval` and client id.

=== Discovery

If the server uses a dedicated discovery endpoint (e.g. `/discovery`), which may support different (less secure) security policies,
then you can make use of this via the parameter `discoveryEndpointSuffix`, which will be appended to the `endpointUri`. Or by using
an explicit `discoveryEndpointUri`.

=== Overriding the host name or port

The client uses the host and port information from the endpoint information, queried from the server. However in some
situations this endpoint URI might be different, and wrong from the point of view of the connecting client (e.g. an
internal hostname or internal port).

In this case it is possible to set the parameter(s) `overrideHost` or `overridePort` to `true`, which will take the
discovered endpoint information, but override the host or port information with the value(s) of the original URI.

[[nodeid]]
=== Node ID

In order to define a target node a namespace and node id is required. In previous versions this was possible by
specifying `nodeId` and either `namespaceUri` or `namespaceIndex`. However this only allowed for using
string based node IDs. And while this configuration is still possible, the newer one is preferred.

The new approach is to specify a full namespace+node ID in the format `ns=1;i=1` which also allows to use the other
node ID formats (like numeric, GUID/UUID or opaque). If the `node` parameter is used the older ones must not be used.
The syntax of this node format is a set of `key=value` pairs delimited by a semi-colon (`;`). 

Exactly one namespace and one node id key must be used. See the following table for possible keys:

[width="100%",cols="2,2,5",options="header"]
|===
| Key | Type | Description
| *ns*  | namespace | Numeric namespace index
| *nsu* | namespace | Namespace URI
| *s*   | node | String node ID
| *i*   | node | Numeric node ID
| *g*   | node | GUID/UUID node ID
| *b*   | node | Base64 encoded string for opaque node ID
|===

As the values generated by the syntax cannot be transparently encoded into a URI parameter value, it is necessary to escape them.
However Camel allows to wrap the actual value inside `RAW(…)`, which makes escaping unnecessary. For example:

----
milo-client:opc.tcp://user:password@localhost:12345?node=RAW(nsu=http://foo.bar;s=foo/bar)
----

=== Monitoring several nodes

A consumer can monitor several nodes with the `nodes` option instead of `node` (the two options cannot be combined).
The consumer creates the monitored items of all nodes together and deletes them together when it stops. Every value
arrives in its own exchange, and the `CamelMiloNodeId` header holds the node ID as it was configured.

The `nodes` option takes a comma-separated list of <<nodeid, Node IDs>>. The entries are trimmed, empty entries are
skipped and a node that is listed twice is monitored once:

----
milo-client:opc.tcp://localhost:12345?nodes=RAW(ns=2;s=line1/temperature,ns=2;s=line1/pressure)
----

A string node ID that contains a comma cannot be used in `nodes`; monitor it with the `node` option instead. Long lists
can come from a property placeholder, for example `+nodes=RAW({{tags}})+`.

All nodes of the list share the `samplingInterval`, `queueSize` and `omitNullValues` options of the consumer and its
monitor filter (`monitorFilterType`, `dataChangeFilter*`). Tags that need a different sampling interval or deadband
need a consumer of their own.

A node that does not exist on the server does not affect the other nodes. A node that cannot be monitored is
reported once with its status code and is not retried; restarting the route or a rebuilt connection to the server creates the monitored items again.
A node whose namespace URI (`nsu=`) is not in the namespace table of the server is reported in the same way.
The consumer delivers one exchange with the bad status code for such a node, and the `CamelMiloNodeId` header names it.

=== Status codes and null values

A data change with a Bad or Uncertain status is always delivered, even when its value is null; `omitNullValues` only
omits a null value with a Good status. This includes the first notification of a monitored item: it carries the current
value of the node, at startup and again after a reconnect, so it can be a Bad status such as `Bad_WaitingForInitialData`
or the status of a `milo-server` item that was not written yet. To skip such a notification, a route filters on its
status code (`getStatusCode()` of the `DataValue` body); a filter on `isGood()` would also drop the Bad status of a
failed sensor.

The default `omitNullValues=true` also omits a null value with a Good status that follows a Bad status, so the route
does not learn that the node recovered. Set `omitNullValues=false` for a node whose value can be null, such as a
`String`.

=== Method ID

It is possible to perform methods calls on OPC UA nodes. If the parameter `method` is set to the Node ID of a method call (the node ID must be set to the parent object in this case),
then a method call will be performed instead of a write operation.

Input parameters are taken from the body:

* If the body is null, then an empty `Variant[]` will be used
* If the body is a `Variant[]`, then it will be used as is
* If the body is a `Variant`, then it will be wrapped in a `Variant[]` array
* Otherwise the body will be converted into a `Variant` and wrapped in an array of `Variant[]`

=== Read Values from Nodes

The component provide a producer to read values from multiple opc-ua nodes. The Node-IDs will be defined in the header `CamelMiloNodeIds` as list of strings. (see <<nodeid, Node-ID>> for the ID format).

Example:

._Java-only: reading values from OPC UA nodes using enrich with an AggregationStrategy_
[source,java]
----
from("direct:start")
    .setHeader("CamelMiloNodeIds", constant(Arrays.asList("nsu=urn:org:apache:camel;s=myitem1")))
    .setHeader("CamelMiloAwait", constant(true)) // CamelMiloAwait: parameter "defaultAwaitWrites"
        .enrich("milo-client:opc.tcp://localhost:4334", new AggregationStrategy() {

            @Override
            public Exchange aggregate(Exchange oldExchange, Exchange newExchange) {
                return newExchange;
            }
        }).to("mock:test1");
----

=== Custom data types: accessing the underlying milo OpcUaClient

Built-in OPC UA data types are read and written transparently. Values whose node has a *custom* (server-defined)
data type are instead returned as an `org.eclipse.milo.opcua.stack.core.types.builtin.ExtensionObject`, which can only
be decoded (or, for writes, encoded) with an `EncodingContext` obtained from the underlying milo client.

The component does not decode these values automatically, because it cannot reliably determine which encoding context
applies. Instead, the active `OpcUaClient` is exposed through `MiloClientConnection.getOpcUaClient()`, so you can obtain
its encoding contexts and perform the encode/decode yourself:

._Java-only: accessing the underlying OpcUaClient for custom data type encoding/decoding_
[source,java]
----
MiloClientEndpoint endpoint = context.getEndpoint("milo-client:opc.tcp://localhost:4334", MiloClientEndpoint.class);
MiloClientConnection connection = endpoint.createConnection();
try {
    OpcUaClient client = connection.getOpcUaClient();
    // dynamic context resolves custom, server-defined types; static context covers built-in/generated types
    EncodingContext encodingContext = client.getDynamicEncodingContext();

    // decode a value read as ExtensionObject
    UaStructuredType decoded = extensionObject.decode(encodingContext);

    // or encode a structure before writing it
    ExtensionObject toWrite = ExtensionObject.encode(encodingContext, myStructure);
} finally {
    endpoint.releaseConnection(connection);
}
----

NOTE: The connection is established lazily and asynchronously, so `getOpcUaClient()` returns `null` until the client is
connected, and again briefly while a connection is being re-established. The client is owned and managed by Camel: do
not connect, disconnect or otherwise change its lifecycle, and fetch it on demand rather than caching the reference, as
a reconnect replaces the instance.

=== Security policies

When setting the allowing security policies is it possible to use the well known OPC UA URIs (e.g. `\http://opcfoundation.org/UA/SecurityPolicy#Basic128Rsa15`)
or to use the Milo enum literals (e.g. `None`). Specifying an unknown security policy URI or enum is an error.

The known security policy URIs and enum literals are can be seen here: https://github.com/eclipse/milo/blob/master/opc-ua-stack/stack-core/src/main/java/org/eclipse/milo/opcua/stack/core/security/SecurityPolicy.java[SecurityPolicy.java]

NOTE: In any case security policies are considered case sensitive.

When `allowedSecurityPolicies` is not set, the client accepts every security policy the server offers and uses the
endpoint with the highest security level reported by the server, which can be `None`. To make sure the connection is
secured, set `allowedSecurityPolicies` to the secured policies you expect the server to offer.

=== Validating the server certificate

When the selected endpoint uses a security policy other than `None`, the client validates the certificate of the
server when it opens the secure channel and the session. Configure the trusted certificates with one of these options:

* `trustListDirectory`: a directory holding the trust list, in the layout used by Eclipse Milo. Put the certificate of
the server, or the certificate of the CA that issued it, in `trusted/certs`. Certificates of intermediate CAs that are
only used to build the chain go in `issuer/certs`, and certificate revocation lists in `trusted/crl` and `issuer/crl`.
The directories are created if they do not exist.
* `certificateValidator`: a custom `org.eclipse.milo.opcua.stack.core.security.CertificateValidator`. It is used
instead of `trustListDirectory` when both are set. Endpoints share a connection only when they use the same validator
instance.

With `trustListDirectory`, the client refuses a server certificate that:

* does not chain up to a certificate in `trusted/certs`, possibly through the certificates in `issuer/certs`,
* is outside its validity period,
* is revoked by a certificate revocation list in `trusted/crl` or `issuer/crl`. A certificate issued by a CA is also
refused, with `Bad_CertificateRevocationUnknown`, when the trust list holds no revocation list of that CA. An empty
CRL signed by the CA is enough. A self-signed certificate in `trusted/certs` is not checked for revocation,
* or holds an application URI that differs from the one the server announces in its endpoint description.

A failed host name, key usage or extended key usage check is only logged. A certificate that does not chain up to a
trusted certificate is written to `rejected/certs`, from where it can be moved to `trusted/certs` once it has been
checked. A certificate refused for another reason is not written there. To use other checks, configure a
`certificateValidator`, for example a `DefaultClientCertificateValidator` created with the `ValidationCheck` set you
need.

If neither option is configured, the client does not connect to an endpoint that uses a security policy other than
`None`. Setting `trustAllCertificates` to `true` makes the client accept any server certificate instead. This is
insecure: the connection is encrypted, but the client does not authenticate the server it talks to.

When the server certificate cannot be validated, the client logs a `WARN` message that starts with `Failed to
connect`, and tries again every 10 seconds, so a certificate moved to `trusted/certs` is used at the next attempt. A
producer fails with `IllegalStateException: No connected`, whose cause gives the reason.

The same validator checks the server certificate that the user name and password are encrypted with. With the
security policy `None`, the server is not authenticated, whatever the configuration.

A secured policy also requires a client certificate and key, configured with `keyStoreUrl` and the related options.
For example:

----
milo-client:opc.tcp://localhost:4840?node=RAW(ns=2;s=Temperature)&allowedSecurityPolicies=Basic256Sha256&keyStoreUrl=file:/etc/opcua/client.p12&keyStorePassword=RAW(changeit)&keyAlias=client&keyPassword=RAW(changeit)&trustListDirectory=/etc/opcua/pki
----

==== Milo 1.0.5 Migration Notes

With Milo 1.0.5, several security-related API changes were introduced:

* The `ServerCertificateValidator` class has been replaced with `CertificateValidator` in the core security package
* Certificate validation now uses `org.eclipse.milo.opcua.stack.core.security.CertificateValidator`
* A validator configured with the `certificateValidator` option must implement this interface
