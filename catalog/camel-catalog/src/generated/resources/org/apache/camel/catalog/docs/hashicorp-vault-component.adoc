== Authentication and HashiCorp Vault on-premise vs HashiCorp Cloud

The component supports operations at the producer level. Specifically, it provides the following functionalities:

* `createSecret`
* `getSecret`
* `deleteSecret`
* `listSecrets`

The component can interact with HashiCorp Vault, which may be deployed either as an on-premise/local instance or as a HashiCorp Vault Cloud instance (Enterprise version).

=== Configuration for HashiCorp Vault Cloud

When using a HashiCorp Vault Cloud instance, in addition to the standard parameters such as `host`, `port`, `scheme`, and `token`, you must configure the following additional parameters:

* `cloud`:: A boolean flag that must be explicitly set to `true` to indicate that the HashiCorp Vault instance is hosted in the cloud.
* `namespace`:: The namespace of your secrets engine. The operations work on `<namespace>/<secretsEngine>`; without a
namespace they work on the secrets engine itself, as on-premise.

=== Logging in to HashiCorp Vault

The `authentication` option chooses how the component logs in to HashiCorp Vault:

[cols="1,3",options="header"]
|===
| Login | Settings

| `token` (the default)
| `token`: a token created in Vault beforehand.

| `approle`
| `roleId` and `secretId`: the role ID and a secret ID of an AppRole.

| `kubernetes`
| `role`: the Vault role of the application. The login sends the service account token of the pod, which it reads from
`/var/run/secrets/kubernetes.io/serviceaccount/token`, or from the file set with `jwtFile`.

| `jwt`
| `jwt`, or `jwtFile` to read the JWT from a file. `role` is the Vault role to log in as, which can be left out when the
JWT login of Vault has a default role.

| `cert`
| `keyStore`: the TLS client certificate, see <<TLS>>. `role` is the name of the certificate role in Vault; without
it, Vault tries every certificate role that trusts the certificate. The login needs the `https` scheme.

| `aws-iam`
| `role`: the Vault role of the application, which logs in with its AWS credentials, see <<Cloud logins>>. Without
`role`, Vault takes the role named as the IAM principal of the application.

| `azure-msi`
| `role`: the Vault role of the application, which logs in with its Azure managed identity, see <<Cloud logins>>.

| `gcp-gce`
| `role`: the Vault role of the application, which logs in with the service account of its Google Compute Engine
instance, see <<Cloud logins>>.
|===

When the login method is not mounted at its default path in Vault (`approle`, `kubernetes`, `jwt`, `cert`, `aws` for
`aws-iam`, `azure` for `azure-msi` or `gcp` for `gcp-gce`), set the path with `authMountPath`, without `auth/`.

Camel renews the token before it expires, and logs in again when the token can no longer be renewed, such as when it
reached its maximum time to live. A JWT read from a file is read again at every login, so a token that the platform
replaces in the file, such as a projected service account token, is picked up. When the endpoint stops, Camel revokes
the token of its login. A token given for the token login is renewed when it is renewable, but never revoked.

On HashiCorp Cloud (`cloud=true` and a `namespace`), the login is made in the namespace, as are the renewal and the
revocation of the token.

For example, an endpoint that logs in with an AppRole, whose role ID and secret ID are in environment variables:

[source,java]
----
from("direct:start")
    .to("hashicorp-vault:secret?operation=getSecret&host=vault.example.com&authentication=approle"
        + "&roleId={{env:VAULT_ROLE_ID}}&secretId=RAW({{env:VAULT_SECRET_ID}})")
    .log("${body}");
----

=== TLS

With the `https` scheme, the component trusts the certificate of Vault as any other TLS connection of the JVM does. For
a Vault whose certificate is signed by a private CA, set `trustStore` to the certificates to trust: a PKCS12 or JKS
trust store with its `trustStorePassword`, or a PEM file with the CA certificates, such as the file that the
`VAULT_CACERT` environment variable of the Vault CLI points to.

To present a client certificate to Vault, for the `cert` login or for a Vault that requires client certificates, set
`keyStore`: a PKCS12 or JKS key store with its `keyStorePassword`, or a PEM file with the certificate and its private
key. The key of a PEM file is not encrypted, in PKCS#8 (`-----BEGIN PRIVATE KEY-----`) or, for an RSA key, in PKCS#1
(`-----BEGIN RSA PRIVATE KEY-----`).

The trust store and the key store are read when the client is created, when the endpoint, the properties function or
the secret refresh task starts. A certificate replaced in its file, such as a client certificate renewed before it
expires, is used after a restart.

For example, the properties function logs in with a client certificate:

[source,properties]
----
camel.vault.hashicorp.host = vault.example.com
camel.vault.hashicorp.port = 8200
camel.vault.hashicorp.scheme = https
camel.vault.hashicorp.trustStore = /etc/vault/ca.pem
camel.vault.hashicorp.authentication = cert
camel.vault.hashicorp.role = my-application
camel.vault.hashicorp.keyStore = /etc/vault/client.pem
----

=== Cloud logins

The `aws-iam` login signs a request to AWS STS with the credentials of the AWS SDK default chain: the environment
variables, the system properties, a web identity token (such as IAM roles for service accounts on Amazon EKS), the
profile, the container credentials (Amazon ECS) or the instance profile (Amazon EC2). Vault checks the request with
STS. The login needs the AWS SDK: add the `software.amazon.awssdk:auth` dependency, in the version of the AWS SDK of
the Camel AWS components. A web identity token also needs the `software.amazon.awssdk:sts` dependency, and an SSO
profile the `software.amazon.awssdk:sso` and `software.amazon.awssdk:ssooidc` dependencies. Without the `sts`
module, the AWS SDK skips the web identity token and takes the next credentials of the chain, such as those of the
instance: so Camel refuses to start the login when a web identity token is set (`AWS_WEB_IDENTITY_TOKEN_FILE`) and
the `sts` module is missing.

The request is sent to `awsStsEndpoint`, by default the global endpoint `https://sts.amazonaws.com/`, which takes
requests signed for `us-east-1`. Without `awsStsEndpoint` and `awsRegion`, the request is signed for `us-east-1`,
whatever the region of the application, as `vault login -method=aws` does. To use a regional endpoint, set
`awsStsEndpoint` and its region in `awsRegion`, as the AWS login of Vault is configured (`sts_endpoint` and
`sts_region`); without `awsRegion`, the request is then signed for the region of the AWS SDK default region chain,
such as the `AWS_REGION` environment variable. `awsIamServerId` sets the `X-Vault-AWS-IAM-Server-ID` header, when the
AWS login of Vault requires one.

For example, the properties function logs in with the AWS credentials of the application, through the STS endpoint
of its region:

[source,properties]
----
camel.vault.hashicorp.host = vault.example.com
camel.vault.hashicorp.port = 8200
camel.vault.hashicorp.scheme = https
camel.vault.hashicorp.authentication = aws-iam
camel.vault.hashicorp.role = my-application
camel.vault.hashicorp.awsStsEndpoint = https://sts.eu-west-1.amazonaws.com
camel.vault.hashicorp.awsRegion = eu-west-1
----

The `azure-msi` login asks the Azure instance metadata service (`169.254.169.254`) for a token of the managed identity
of the virtual machine, for the resource `azureResource`, by default `https://management.azure.com/`, which must be
the resource of the Azure login of Vault (`auth/azure/config`). `azureClientId` chooses a user-assigned managed
identity, instead of the system-assigned one. The instance metadata service is on Azure virtual machines and scale
sets. A pod of Azure Kubernetes Service with workload identity has a token in the file named by the
`AZURE_FEDERATED_TOKEN_FILE` environment variable instead, for the `jwt` login with `jwtFile`.

The `gcp-gce` login asks the metadata server of a Google Compute Engine instance for an identity token of the default
service account of the instance, for a role of type `gce` of the GCP login of Vault.

The metadata services are reached directly, never through an HTTP proxy.

=== OpenBao

The component, the properties function and the secret refresh task also work with https://openbao.org/[OpenBao], the
open source fork of HashiCorp Vault, which keeps the API of Vault. OpenBao has the token, AppRole, Kubernetes, JWT and
TLS certificate logins built in.


== Examples

=== Using the producer operations

The producer works on a secrets engine, given as the path of the endpoint (`secret` is the default key/value
engine), and connects with the `host`, `port`, `scheme` and `token` endpoint options. The `operation` option
selects what to do, and `secretPath` names the secret to work on; the `CamelHashicorpVaultProducerOperation`
and `CamelHashicorpVaultSecretPath` headers override them per message.

==== Creating a secret

The message body is the map of key/value pairs to store as the secret. A POJO is written as JSON, and text, bytes,
a stream or a file must hold a JSON object of the fields. A message without a body fails, instead of writing a new,
empty version of the secret:

[tabs]
====
Java::
+
[source,java]
----
from("direct:createSecret")
    .to("hashicorp-vault:secret?operation=createSecret&secretPath=database&host=localhost&port=8200&scheme=http&token={{vault.token}}");
----

XML::
+
[source,xml]
----
<camelContext>
    <route>
        <from uri="direct:createSecret"/>
        <to uri="hashicorp-vault:secret?operation=createSecret&amp;secretPath=database&amp;host=localhost&amp;port=8200&amp;scheme=http&amp;token={{vault.token}}"/>
    </route>
</camelContext>
----

YAML::
+
[source,yaml]
----
- route:
    from:
      uri: direct:createSecret
      steps:
        - to:
            uri: hashicorp-vault:secret?operation=createSecret&secretPath=database&host=localhost&port=8200&scheme=http&token={{vault.token}}
----
====

==== Getting a secret

The message body becomes a Map with the fields of the secret under `data` and its version details under
`metadata`, or no body when the secret does not exist; the `CamelHashicorpVaultSecretVersion` header reads a given
version (a number) instead of the latest:

[tabs]
====
Java::
+
[source,java]
----
from("direct:getSecret")
    .to("hashicorp-vault:secret?operation=getSecret&secretPath=database&host=localhost&port=8200&scheme=http&token={{vault.token}}")
    .log("The database secret is ${body}");
----

XML::
+
[source,xml]
----
<camelContext>
    <route>
        <from uri="direct:getSecret"/>
        <to uri="hashicorp-vault:secret?operation=getSecret&amp;secretPath=database&amp;host=localhost&amp;port=8200&amp;scheme=http&amp;token={{vault.token}}"/>
        <log message="The database secret is ${body}"/>
    </route>
</camelContext>
----

YAML::
+
[source,yaml]
----
- route:
    from:
      uri: direct:getSecret
      steps:
        - to:
            uri: hashicorp-vault:secret?operation=getSecret&secretPath=database&host=localhost&port=8200&scheme=http&token={{vault.token}}
        - log:
            message: "The database secret is ${body}"
----
====

The secret can also be chosen per message with the `CamelHashicorpVaultSecretPath` header:

[tabs]
====
Java::
+
[source,java]
----
from("direct:getSecret")
    .setHeader(HashicorpVaultConstants.SECRET_PATH, constant("database"))
    .to("hashicorp-vault:secret?operation=getSecret&host=localhost&port=8200&scheme=http&token={{vault.token}}");
----

XML::
+
[source,xml]
----
<camelContext>
    <route>
        <from uri="direct:getSecret"/>
        <setHeader name="CamelHashicorpVaultSecretPath">
            <constant>database</constant>
        </setHeader>
        <to uri="hashicorp-vault:secret?operation=getSecret&amp;host=localhost&amp;port=8200&amp;scheme=http&amp;token={{vault.token}}"/>
    </route>
</camelContext>
----

YAML::
+
[source,yaml]
----
- route:
    from:
      uri: direct:getSecret
      steps:
        - setHeader:
            name: CamelHashicorpVaultSecretPath
            expression:
              constant:
                expression: database
        - to:
            uri: hashicorp-vault:secret?operation=getSecret&host=localhost&port=8200&scheme=http&token={{vault.token}}
----

=== Using HashiCorp Vault Property Function

To use this function, you'll need to provide credentials for HashiCorp Vault as environment variables:

[source,bash]
----
export CAMEL_VAULT_HASHICORP_TOKEN=token
export CAMEL_VAULT_HASHICORP_HOST=host
export CAMEL_VAULT_HASHICORP_PORT=port
export CAMEL_VAULT_HASHICORP_SCHEME=http/https
----

You can also configure the credentials in the `application.properties` file such as:

[source,properties]
----
camel.vault.hashicorp.token = token
camel.vault.hashicorp.host = host
camel.vault.hashicorp.port = port
camel.vault.hashicorp.scheme = scheme
----

In case the running HashiCorp Vault instance you're pointing is running on HashiCorp Cloud, the configuration will require two additional parameters:

[source,bash]
----
export CAMEL_VAULT_HASHICORP_TOKEN=token
export CAMEL_VAULT_HASHICORP_HOST=host
export CAMEL_VAULT_HASHICORP_PORT=port
export CAMEL_VAULT_HASHICORP_SCHEME=http/https
export CAMEL_HASHICORP_VAULT_CLOUD=true
export CAMEL_HASHICORP_VAULT_NAMESPACE=namespace
----

You can also set the same in the `application.properties` file such as:

[source,properties]
----
camel.vault.hashicorp.token = token
camel.vault.hashicorp.host = host
camel.vault.hashicorp.port = port
camel.vault.hashicorp.scheme = scheme
camel.vault.hashicorp.cloud = true
camel.vault.hashicorp.namespace = namespace
----

This will make the Properties function works even in the HashiCorp Cloud deployment option.

The properties function logs in with a token by default. To log in another way, set the options of
<<Logging in to HashiCorp Vault>> with the `camel.vault.hashicorp` prefix. For example, an application in a Kubernetes
pod logs in with the service account of the pod:

[source,properties]
----
camel.vault.hashicorp.host = vault.example.com
camel.vault.hashicorp.port = 8200
camel.vault.hashicorp.scheme = https
camel.vault.hashicorp.authentication = kubernetes
camel.vault.hashicorp.role = my-application
----

The properties function also reads these options from the environment variables `CAMEL_HASHICORP_VAULT_AUTHENTICATION`,
`CAMEL_HASHICORP_VAULT_ROLE_ID`, `CAMEL_HASHICORP_VAULT_SECRET_ID`, `CAMEL_HASHICORP_VAULT_ROLE`,
`CAMEL_HASHICORP_VAULT_JWT`, `CAMEL_HASHICORP_VAULT_JWT_FILE` and `CAMEL_HASHICORP_VAULT_AUTH_MOUNT_PATH`, and the
settings of <<TLS>> from `CAMEL_HASHICORP_VAULT_TRUST_STORE`, `CAMEL_HASHICORP_VAULT_TRUST_STORE_PASSWORD`,
`CAMEL_HASHICORP_VAULT_KEY_STORE` and `CAMEL_HASHICORP_VAULT_KEY_STORE_PASSWORD`, and the settings of the <<Cloud
logins>> from `CAMEL_HASHICORP_VAULT_AWS_IAM_SERVER_ID`, `CAMEL_HASHICORP_VAULT_AWS_REGION`,
`CAMEL_HASHICORP_VAULT_AWS_STS_ENDPOINT`, `CAMEL_HASHICORP_VAULT_AZURE_RESOURCE` and
`CAMEL_HASHICORP_VAULT_AZURE_CLIENT_ID`. When any of the `CAMEL_HASHICORP_VAULT_*` environment variables is set, the
properties function takes all its settings from the environment variables, and none from the `camel.vault.hashicorp`
configuration. The secret refresh task logs in the same way as the properties function.

NOTE: if you're running the application on a Kubernetes based cloud platform, you can initialize the environment variables from a Secret or Configmap to enhance security. You can also enhance security by xref:manual::using-propertyplaceholder.adoc#_resolving_property_placeholders_on_cloud[setting a Secret property placeholder] which will be initialized at application runtime only.

NOTE: `camel.vault.hashicorp` configuration only applies to the HashiCorp Vault properties function (E.g when resolving properties).
When using the `operation` option to create, get, list secrets etc., you should provide the `host`, `port`, `scheme` (if required) and the options of the login, such as `token`.

At this point, you'll be able to reference a property in the following way:

[tabs]
====
Java::
+
[source,java]
----
from("direct:start")
    .to("{{hashicorp:secret:route}}");
----

XML::
+
[source,xml]
----
<camelContext>
    <route>
        <from uri="direct:start"/>
        <to uri="{{hashicorp:secret:route}}"/>
    </route>
</camelContext>
----

YAML::
+
[source,yaml]
----
- route:
    from:
      uri: direct:start
      steps:
        - to:
            uri: "{{hashicorp:secret:route}}"
----
====

Where route will be the name of the secret stored in the HashiCorp Vault instance, in the 'secret' engine.

NOTE: The engine is the part before the first `:`; for a property with a field, only the part before the `#` counts.
When the property has no engine, such as `{{hashicorp:route}}` or `{{hashicorp:database#username}}`, the secret is read
from the 'secret' engine. Without a field, a default value needs the engine, as in `{{hashicorp:secret:route:default}}`:
in `{{hashicorp:route:default}}` the engine would be `route`. With a field it does not, as in
`{{hashicorp:database#username:admin}}`.

You could specify a default value in case the secret is not present on HashiCorp Vault instance:

[tabs]

[source,java]

    .to("{{hashicorp:secret:route:default}}");
----

XML::

[source,xml]

<camelContext>
    <route>
        <from uri="direct:start"/>
        <to uri="{{hashicorp:secret:route:default}}"/>
    </route>
</camelContext>
----

YAML::
+
[source,yaml]

    from:
      uri: direct:start
      steps:
        - to:

----

In this case, if the secret doesn't exist in the 'secret' engine, the property will fall back to "default" as value.

=== Automatic Camel context reloading on Secret Refresh

Being able to reload Camel context on a Secret Refresh could be done by specifying the usual credentials (the same used for HashiCorp Vault Property Function).

With Environment variables:

[source,bash]
----
export CAMEL_HASHICORP_VAULT_TOKEN=token
export CAMEL_HASHICORP_VAULT_HOST=host
export CAMEL_HASHICORP_VAULT_PORT=port
export CAMEL_HASHICORP_VAULT_SCHEME=http/https
----

or as plain Camel main properties:

[source,properties]
----
camel.vault.hashicorp.token = token
camel.vault.hashicorp.host = host
camel.vault.hashicorp.port = port
camel.vault.hashicorp.scheme = scheme
----

To enable the automatic refresh, you'll need additional properties to set:

[source,properties]
----
camel.vault.hashicorp.refreshEnabled=true
camel.vault.hashicorp.refreshPeriod=60000
camel.vault.hashicorp.secrets=database,api-keys
camel.main.context-reload-enabled = true
----

where `camel.vault.hashicorp.refreshEnabled` will enable the automatic context reload, `camel.vault.hashicorp.refreshPeriod` is the interval of time between two different checks for update events (default 60000ms), and `camel.vault.hashicorp.secrets` is a comma-separated list of secret names (or patterns) to check for updates.

The secret names should use the following format:
- `mysecret` or `path/to/secret` - tracks a secret in the default `secret` engine
- `myengine:mysecret` or `myengine:path/to/secret` - tracks a secret in the `myengine` engine (use `:` to separate engine from path)
- You can use patterns like `database*` to match multiple secrets

Note that `camel.vault.hashicorp.secrets` is not mandatory: if not specified the task responsible for checking updates events will take into account all the properties with a `hashicorp:` prefix.
Such a secret is tracked in the engine of the property, in the format above (`hashicorp:myengine:mysecret` is tracked as `myengine:mysecret`, `hashicorp:secret:mysecret` as `mysecret`), and its first check compares the version in Vault with the version that was resolved, so an update made before the first check also triggers a reload.

==== How the Refresh Mechanism Works

Unlike cloud-based secret managers (AWS, GCP, Azure) that provide event-driven notifications, HashiCorp Vault does not have a native event notification system for secret changes. Therefore, this implementation uses a **polling-based approach**:

1. **Metadata Polling**: The refresh task periodically queries the HashiCorp Vault metadata endpoint (`/v1/<engine>/metadata/<secret>`) for each tracked secret.
2. **Version Tracking**: It compares the `current_version` field to detect changes.
3. **Change Detection**: When a version change is detected, it triggers a Camel context reload.
4. **Efficiency**: Only metadata is queried (not the full secret content), making this approach lightweight.

For example, if a secret named `database` is updated in Vault:
- The metadata endpoint returns `"current_version": 5`
- On the next check, if `current_version` changes to `6`, a reload is triggered
- The refresh period (default 60 seconds) determines how quickly changes are detected

This polling approach works with all HashiCorp Vault deployments (on-premise, cloud, enterprise, and open-source) without requiring additional infrastructure.


=== Using HashiCorp Vault Property Function in Spring Boot for Early resolving properties

HashiCorp Vault Spring Boot component starter offers the ability to early resolve properties, so the end user could resolve properties directly in the application.properties before both Spring Boot runtime and Camel context will start.

This could be accomplished in the following way. You should specified this property in your application.properties file:

[source,bash]
----
camel.component.hashicorp-vault.early-resolve-properties=true
----

This will enable the feature so you'll be able to resolved properties, in your application.properties file, like:

[source,bash]
----
foo = hashicorp:secret:database/password#string
----
