*Since Camel {since}*

*{component-header}*

The *couchbase:* component allows you to treat
https://www.couchbase.com/[Couchbase] instances as a producer or consumer
of messages.

Maven users will need to add the following dependency to their `pom.xml`
for this component:

[source,xml]
----
<dependency>
    <groupId>org.apache.camel</groupId>
    <artifactId>camel-couchbase</artifactId>
    <version>x.x.x</version>
    <!-- use the same version as your Camel core version -->
</dependency>
----

== Consuming documents

The consumer supports two query modes for polling documents from Couchbase:

=== SQL++ queries (recommended, default)

Since Couchbase Server 7.0, the recommended way to query documents is using SQL++ (formerly N1QL).
MapReduce Views are deprecated since Couchbase 7.0 and do not work with the Magma storage backend
(default since Couchbase 8.0).

By default, the consumer uses SQL++ queries. You can either provide an explicit `statement` or
let the consumer auto-generate one from the endpoint options.

==== Auto-generated queries

The simplest way to consume documents is to just use the existing endpoint options. The consumer
auto-generates a SQL++ query from `bucket`, `collection`, `limit`, `skip`, `descending`,
`rangeStartKey`, and `rangeEndKey`:

[tabs]
====
Java::
+
[source,java]
----
from("couchbase:http://localhost?bucket=myBucket&username=user&password=pass&limit=10&descending=true")
    .to("direct:result");
----

XML::
+
[source,xml]
----
<route>
  <from uri="couchbase:http://localhost?bucket=myBucket&amp;username=user&amp;password=pass&amp;limit=10&amp;descending=true"/>
  <to uri="direct:result"/>
</route>
----

YAML::
+
[source,yaml]
----
- route:
    from:
      uri: couchbase:http://localhost
      parameters:
        bucket: myBucket
        username: user
        password: pass
        limit: 10
        descending: true
      steps:
        - to:
            uri: direct:result
----
====

This generates: `SELECT META().id AS \__id, * FROM \`myBucket\`.\`_default\`.\`_default\` AS \`myBucket\` ORDER BY META().id DESC LIMIT 10`

The query runs on the scope of the endpoint (the default scope when `scope` is not set). With the `collection`
option, the query reads that collection of the scope (`FROM \`myCollection\``). Without it, the query reads the
default collection of the bucket, which is the collection the consumer fetches the documents from.

==== Explicit SQL++ statements

For complex queries (filters, joins, aggregations), set the `statement` option directly:

._Java-only: string concatenation in endpoint URI_
[source,java]
----
from("couchbase:http://localhost?bucket=myBucket&username=user&password=pass"
    + "&statement=SELECT META().id AS __id, * FROM `_default` WHERE type = 'order' LIMIT 100")
    .to("direct:result");
----

The query must include `META().id AS \__id` in the SELECT clause so the consumer can identify each document.

The statement runs on the scope of the endpoint (the default scope when `scope` is not set), so a single name in
`FROM` is a collection of that scope: in the default scope, `FROM \`_default\`` is the default collection of the
bucket, and the bucket name alone fails with "Keyspace not found". Use the full path `\`bucket\`.\`scope\`.\`collection\`` for a collection of
another scope.

When `fullDocument` is `true` (the default), the consumer fetches the document from the KV store by its id, and the
message body is the `GetResult` of the Couchbase SDK, with the id in the `CamelCouchbaseId` header: `contentAsObject()`
gives the JSON document. When `false`, the message body is the query result row as JSON text, or with views the value the
view emits.

NOTE: SQL++ queries require a primary index or appropriate secondary index on the bucket/collection.
Create one with: `CREATE PRIMARY INDEX ON \`myBucket\`` or via the Couchbase SDK.

=== MapReduce Views (deprecated)

The consumer can also poll documents using MapReduce Views by setting `useView=true` with the
`designDocumentName` and `viewName` endpoint options. This mode is deprecated and will be removed
in a future release.

._Java-only: string concatenation in endpoint URI_
[source,java]
----
from("couchbase:http://localhost?bucket=myBucket&username=user&password=pass"
    + "&useView=true&designDocumentName=myDoc&viewName=myView&limit=10")
    .to("direct:result");
----

Reduce views and compound keys work in view mode too. A row of a reduce view has no document ID: its value is the
message body, with or without `fullDocument`, and the `CamelCouchbaseId` header is not set. A key that is not a
string, such as the compound key `[2024, "orders"]`, is set in the `CamelCouchbaseKey` header as its JSON text.

=== Migrating from Views to SQL++

To migrate from MapReduce Views to SQL++, simply remove `designDocumentName` and `viewName` from
your endpoint URI. The `limit`, `skip`, `descending`, `rangeStartKey`, and `rangeEndKey` options
are automatically translated to SQL++ clauses:

[cols="1,1",options="header"]
|===
| View option | SQL++ equivalent

| `designDocumentName` + `viewName`
| Removed (or replaced by `statement` for custom queries)

| `limit=10`
| `LIMIT 10`

| `skip=5`
| `OFFSET 5`

| `descending=true`
| `ORDER BY META().id DESC`

| `rangeStartKey=A` / `rangeEndKey=Z`
| `WHERE META().id >= 'A' AND META().id \<= 'Z'`

| `fullDocument=true`
| Works the same way in both modes
|===

For example, a view-based consumer:

._Java-only: string concatenation in endpoint URI_
[source,java]
----
from("couchbase:http://localhost?bucket=myBucket&username=user&password=pass"
    + "&useView=true&designDocumentName=myDoc&viewName=myView&limit=10&descending=true")
----

Can be migrated by simply removing the view-specific options:

._Java-only: string concatenation in endpoint URI_
[source,java]
----
from("couchbase:http://localhost?bucket=myBucket&username=user&password=pass"
    + "&limit=10&descending=true")
----

Or with an explicit SQL++ statement for more control:

._Java-only: string concatenation in endpoint URI_
[source,java]
----
from("couchbase:http://localhost?bucket=myBucket&username=user&password=pass"
    + "&statement=SELECT META().id AS __id, * FROM `_default` ORDER BY META().id DESC LIMIT 10")
----

== Producing documents

The producer works on one document per message. The document id is the `CamelCouchbaseId` header, or the `key`
option when the message has no such header. The call fails when neither gives an id, unless `autoStartIdForInserts`
is enabled, which gives every document the next number as id. The producer leaves the `CamelCouchbaseId` header on
the message, so a `CCB_GET` after a `CCB_PUT` in the same route reads the document the `CCB_PUT` stored.

The `operation` option is one of the following; any other value fails when the producer starts:

[cols="1,3,2",options="header"]
|===
| Operation | What it does | Message body afterwards

| `CCB_PUT` (default)
| Stores the message body as the document (an upsert), with the expiry of the `CamelCouchbaseTtl` header
| `true`

| `CCB_GET`
| Reads the document
| The `GetResult` of the SDK, for example `getBody(GetResult.class).contentAsObject()`

| `CCB_DEL`
| Removes the document
| The text of the `MutationResult` of the SDK
|===

`CCB_PUT` stores the message body as follows:

[cols="1,3",options="header"]
|===
| Message body | Stored as

| Text (`String`) holding a JSON object or array
| That JSON document, as it is (`RawJsonTranscoder`)

| Other text
| A JSON string

| `byte[]` holding a JSON object or array
| That JSON document, as it is (`RawJsonTranscoder`)

| Other `byte[]`
| A binary document (`RawBinaryTranscoder`); read it with `contentAsBytes()`

| A stream (`InputStream` or stream cache)
| Read as bytes, and then stored as a `byte[]` body is

| A `Map`, a `List`, a `JsonObject`, a `JsonArray` or a POJO
| A JSON document, serialized by the SDK
|===

== Couchbase SDK compatibility

Using collections and scopes is supported only for Couchbase Server 7.0 and later.

This component is currently using Java SDK 3.x, so it might be not compatible with older Couchbase servers anymore.
Check the compatibility https://docs.couchbase.com/java-sdk/current/project-docs/compatibility.html[page] for details.

 * The value formerly interpreted as a bucket-name is now interpreted as a username. The username must correspond to a user defined on the cluster that is being accessed.
 * The value formerly interpreted as a bucket-password is now interpreted as the password of the defined user.
